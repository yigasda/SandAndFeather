# 상인 캐시 복구·회전 HUD 수정 (미발행)

기존 확대율/세로 UI 수정 `56cd1507447bc3c2ad4e09a967133f95c9dc877f` 위의 별도 수정이다. main/release 발행은 하지 않는다. 신규 그림·NPC·저장 형식·AI 분석 로직은 추가하지 않는다.

## 실제 실패 재현과 수정

### 상인

상인은 실제 출시 `data/maps/ombos.json`의 merchant/townsman이며 가상 NPC를 추가하지 않았다. 동행 3인방은 동작 아틀라스를 직접 읽지만 상인의 정적 그림은 Renderer.art의 잘라 둔 캔버스를 사용한다. 기존 `repaint()`는 맵만 재생성했고, 정적 스프라이트 캔버스의 contextrestored 처리도 없었다.

상인 캐시 캔버스를 비운 뒤 복구 이벤트를 주입하면 맵에는 merchant가 남고 동행도 보이지만 상인 그림은 2,125 불투명 픽셀에서 0으로 사라졌다. 기존 커밋 56cd1507을 라우팅한 재현에서 메인 contextrestored, 상인 캔버스 contextrestored, visibilitychange, close/open 네 경로 모두 0이었다. **캔버스 손실을 모델링한 결함 주입이며, 사용자 기기의 GPU 손실을 직접 관측한 로그라고 주장하지 않는다.**

복구 때 디코드된 기존 원본으로 정적 스프라이트 캐시도 다시 구성하고, 개별 캐시 캔버스의 복구 이벤트도 처리한다. 프레임마다 재생성하지 않는다. 사진과 같은 실제 시장 데이터·시간 조건을 별도로 확인했고, 강제 이미지 요청 실패 뒤 800ms 지연 재시도에서도 미완성 게임 화면을 열지 않고 decode 후 상인이 구성됨을 검증했다. 이미지 로드 실패/지연 경로는 기존 재시도 처리가 정상이며 그 코드는 변경하지 않았다.

### 이벤트 안내와 날짜판

사용자가 보낸 정상/불량 사진에 대한 부모의 직접 관측을 기준으로 했다. 기존 가로 CSS는 모험등급을 order:-1로 앞에 배치하고, 안내 시작점을 고정 높이로 두고 있었다. 사용자 수치(9/18, 189, 모험등급 6)로 실제 release를 재현하면 순서가 모험등급→수치→금화였고 안내 간격 29px, 오른쪽 끝 불일치 약9.08px, 날짜 높이/글자 크기 비율 4였다. 회전 후에도 같은 잘못된 규칙이 적용됐다.

- 원래 DOM 순서인 수치→금화→모험등급으로 복원.
- ResizeObserver로 수치 칸들의 실제 좌우 끝과 가장 아래 줄을 측정해 안내 폭을 같게, 간격을 6px로 유지. 창 열기/회전/viewport resize/폰트 크기 변경 후 재측정하며 오래된 고정 폭을 저장하지 않는다.
- 가로 날짜판은 한 줄, 34px 높이/14px 글자(약2.43배), 얇은 5px 프레임. 배경의 세로 반복을 없애 여러 가로줄이 늘어나는 현상을 방지. 세로의 테마별 보조 문구 표시 정책은 보존한다.
- 확대된 글자에서 기존판은 5개 테마 × 세로/좁은 가로 총10조건에서 안내와 상태 칸이 겹쳤다. 수정본은 글자 확대·실제 CDP orientationchange/resize·창 닫기/열기 이후에도 겹치지 않으며 글자 크기를 줄이면 패널도 위로 돌아온다.

## 검사 해석

- 이전 NPC 검사에서 `morning`을 쓴 것은 오류였다. 정식 값 `dawn`으로 수정하고 실제 scene.part 일치를 확인한다. 하티르 8일, 실제 시장/상인으로 검사한다.
- 초기 복구/레이아웃 테스트는 세로의 모든 테마가 보조 설명을 표시한다고 잘못 가정했다. 기존 테마 중 cozy만 표시하고 다른 네 테마는 숨긴다. 이 기대값을 기존 정책에 맞춰 수정했으며 제품 스타일을 억지로 바꾸지 않았다.
- 환경 재기동으로 ffmpeg 임시 링크가 없어 첫 출입구 검사는 페이지 생성 전에 실패했다. 설치된 `/usr/bin/ffmpeg`를 기존 Playwright 경로에 연결한 뒤 다시 검사했다.
- 새 디자인 정보를 반영하는 동안 앞선 묶음은 이미 시험 서버에 복사된 이전 스냅샷으로 끝났다. 앞선 UI 결과를 새 레이아웃의 결과로 쓰지 않고, 변경 후 UI 3종·가로/세로·줌을 다시 검사한다. 렌더러 바이트가 동일한 상인 이미지 재시도/일반 NPC 검사 결과는 재사용한다.

## 이동·문 통과 실패 원인과 수정

두 실패는 별개였다. 통검사 통과로 덮지 않고 실패 조건을 따로 재현했다.

1. `portal-walk --exit-lifecycle`의 `키보드 유지+패드 취소: 남은 이동 입력을 중립으로 오인하지 않음`, `실제 키보드로 출구 이탈 후 재무장` assertion 실패: `logs/keyboard-focus-failure.log`에서 방향키 target/active가 TEXTAREA였다. 게임의 `typing(e)` 보호가 정상 동작한 시험 초점 문제다. 해당 시퀀스 전에 초점을 비우고 입력란이 아닌지 확인하도록 시험만 고쳤다. 타이핑 중 이동 차단 제품 코드는 유지한다.
2. `verify-full-map.cjs:30` 사원 문 진입 timeout은 별도 실제 게임 결함이었다. 업데이트 전에는 모든 맵 도착에 `doorNeedsNeutral=true`를 넣었다. 이미 입력이 중립이어도 다음 RAF 이전에 새 키가 들어오면 그 중립을 놓쳤다. 출구 위까지 걸은 뒤 계속 잠긴다. 도착 순간 `Math.hypot(input.dx,input.dy)>0.15`인 경우에만 중립을 요구하도록 수정했다.

결정적 재현은 RAF를 도착 전 잠시 정지했다가 실제 키 입력 뒤 다시 시작해 정상 프레임 사이의 순서를 고정한다. 옴보스 `(24.9,10.6)`, 입력 `(0,0)`, BODY 초점, 팝업 없음, 이동 Promise 없음, 활성 overlay 없음에서 시작한다. 수정 전 위 키 유지 시 `(24.9,9.19678)`, 발 `(25.4,9.99678)`에서 사원 출구 안인데 `doorNeedsNeutral=true`, `doorArmed=false`로 남았다. 발 위치 충돌은 false다. 콘솔에는 시험 ST의 기존 시작 JSON 오류(Internal S)가 별도로 기록되며 게임 예외는 없다. 실제 사용자폰에서 이 스케줄을 관측했다고 주장하지 않는다.

- `door-before-detailed/result-0.json`: 동일 조건에 원래 잠금 한 줄만 복원한 음성 대조군. 예상대로 사원 진입 assertion 실패.
- `door-after/result-{0,1,2}.json`: 동일 조건 3회 모두 `temple_courtyard` 진입. 각 회차에서 반대 조건(키를 누른 채 도착)은 계속 잠기고 놓은 뒤 해제되어 연속 출입구 전환 방지도 유지. 총6개 assertion 통과.
- 초점 수정 뒤 출입구 수명주기 14개 assertion도 3회 연속 통과. 원래 UI 3종 중 전체맵 검사와 가로 입력/줌 검사도 제품 수정 후 다시 통과했다.
- 문 잠금 회귀는 일반 지형에서 배경까지 멎는 성능 제보와 같은 원인이라고 단정하지 않는다.

## 일반 이동 버벅임: 조사 결과와 한계

사용자는 녹화 없이도 동일하다고 확인했다. 녹화만의 문제로 보지 않는다. 영상은 배경/캐릭터가 함께 약0.23~0.43초 멎었다 이동하며, 단순 애니메이션 문제로 축소하지 않는다.

0.9.91 release `179b29b0f8fc28e71b013774994871d0679fc226`, 0.9.92 release `3dbbde3d4b94a291f7f6ffa81af2abc2d7426de5`, 현재 수정본을 실제 ST8001에서 소스/자산 라우팅해 비교했다. viewport390×844/DPR2/CPU4배 지연, 실제 touch 입력이며 사용자폰과 동등한 환경이라고 주장하지 않는다.

- `movement-first`: 옴보스/황금사구 같은 출발점과 충돌 없는 좌우 경로. 각600ms 입력을10회 누르고 놓았다. 첫 사막0.9.92 RAF최대283ms 및254ms longtask가 관측되었으나 정지 구간과 입력유지 구간을 원자료로 분리하지 못한다. 정지8fps/걷기30fps 정책 때문에 이를 걷기FPS로 쓰지 않는다.
- `movement-cpu`: 사막 같은조건 재측정과CPU프로파일. RAF최대 이전116.7ms/현재133.3ms/수정본116.6ms로 첫회 차이가 지속되지 않았다. ST DOM탐색/jQuery 이벤트 비용은 세 버전 모두 존재하며 특정 신규 코드의 병목이라는 인과증거는 없다. 게임frame 누적은 약541/483/553ms로 CPU회귀도 확정 못 했다. 브라우저/프로파일 오버헤드와 실행 변동이 있다.
- `movement-held`: 옴보스에서 **touchEnd 없이** 방향만 좌우로10회 바꾸며 입력/캐릭터/카메라/캔버스/줌을 함께 계측한 보완 검사. 실제 캔버스780×1688, 줌4 동일. 모든 버전 resize·setSprites0회, 좌표측정10회. 입력→동일방향 첫draw 최대17.2/17.0/16.6ms, 카메라는 매프레임 현재 캐릭터와 경계계산 값에 정확히 일치했다. 줌도 고정이었다.

|---|---:|---:|---:|
| draw 처리시간P95(ms) |21.9|15.3|17.1|

이 보완 조건에서는 영상의 멈춤을 재현하지 못했고 게임 성능 회귀/기기 문제 어느 쪽도 확정하지 않았다. dt최대0.2초, 이동분할0.05초, 걷기30fps는 이전에도 존재한다. 지연 뒤 위치 점프를 설명하지만 지연을 유발한 원인의 증거는 아니다. 근거 없는 성능 코드 변경은 추가하지 않았다. **일반 이동 버벅임은 수정 완료가 아니다.** 다음 실기기 계측에는 사용자의 실제 폰/브라우저 또는 ST 앱/WebView 종류가 먼저 필요하다. 현재 자료는 문 잠금 수정의 안전성 증거와 구분한다.
