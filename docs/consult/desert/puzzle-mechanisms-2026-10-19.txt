0. 최신 논의와 원문 적용 범위

[최신 대화에서 논의한 구현 방향]
- Opus가 퍼즐 기믹과 상태·저장 설계를 먼저 진행한다. 최종 그림은 나중에 기존 픽셀아트에 맞춘다.
- 거울·문양·상형문자 퍼즐은 맵에서 장치를 조사하면 모바일용 전용 오버레이 화면을 여는 방향이다.
- 돌 운반·압력판처럼 위치와 이동이 핵심인 조작은 월드에서 다루는 방향이다. 다만 원문에 구체적으로 있는 것은 운반 봉인석과 소켓이다. 압력판의 개수·배치·발동 조건·정답·보상은 원문에 없으므로 이미 설계된 장치처럼 추가하지 않는다.

- 이는 기존 배경을 바꾸거나 수신부를 아래로 옮기는 승인이 아니다. 원문의 상단 뒷단 수신부 및 높이 제약은 부록에 보존하며, 향후 배경 통합을 선택할 때 다시 검토한다.
- 임시 도형·임시 UI를 쓰고 PNG 교체와 논리 규칙을 분리한다. 지금 새 원화나 최종 픽셀아트를 생성하지 않는다. 기존 채택 원화도 재생성하지 않는다.
- 전용 화면의 구체 배치와 16의 월드 운반석↔오버레이 연결 방식은 설계할 항목이다. 원문에 존재하는 완성 UI로 취급하지 않는다.

[별도 제안: 원문 명세나 승인된 세부 동작이 아님]
- 오버레이를 여는 동안 필드 진행·필드 입력을 잠시 멈추고, 닫을 때 안전하게 복귀시키는 운영안을 제안한다. 정지 범위·저장 시점·닫기 동작은 구현 전 검토한다.

2. 데이터·ID 계약
근거: 원문 2절. 아래 필드·ID는 원문 설계 제안이며 실제 API 이름이 아니다.

정적 정의와 저장 상태를 분리한다.
- 맵 정의: 의미 기반 mapId, 표시명, 지역, 에셋 참조, 논리 경계, 보행 영역, 정적 광선 장애물, 출입구, 오브젝트 배치, 단서 참조, 제작 상태.
- 퍼즐 정의: puzzleId, definitionVersion, 장치와 합법 조작, 초기 상태, 해결 규칙, 완료 유지 정책, 보상 참조, 필수 단서, 개발자 해답 증거.
- 맵 런타임: 로딩 중 이미지·렌더 캐시·선택 대상·광선 선분·입력 잠금. 저장하지 않는 파생 데이터다.
- 채팅별 월드 상태: 방문·발견, 퍼즐 가변 상태, 단서, 통로 개방, 고유 보상 수령, 유물 단계와 전시, 안전 귀환점.

숫자와 T/P 번호는 제작용 표기다. 배열 인덱스나 표시명을 저장 키로 쓰지 않는다. 예시 ‘desert.lightwell’, ‘desert.colonnade’, ‘puzzle.desert.lightwell.main’, ‘device.lightwell.mirror_a’는 제안 ID이며 현재 코드의 실제 ID가 아니다. 한 번 배포한 의미 ID는 정렬·번역·파일명 변경으로 바꾸지 않는다. 여러 맵에서 공용 거울 그림을 쓰더라도 장치 인스턴스 ID는 서로 달라야 한다.

ID 네 층을 혼동하지 않는다.
- assetId 는 재사용 가능한 그림.
- objectId 는 맵 안 한 배치물.
- puzzleId 는 여러 배치물을 묶은 규칙.
- rewardId 는 같은 채팅에서 지급을 한 번만 인정할 고유 권리.

맵 이름이 바뀌면 표시명만 바꾼다. 맵을 합치면 옛 ID 를 별칭으로 남기고 위치·단서·완료·보상을 새 소유 맵에 명시적으로 매핑한다. 기존 사막 방문 하나를 신규 맵 모두 발견한 것으로 변환하지 않는다. 기존 보유품과 완료 보상은 실제 대응 근거를 확인해 보존한다.

원문의 전체 34개 공간의 제작 번호와 의미 ID 를 연결하는 검토용 등록부를 둔다. 필수 검증은 ID 중복 없음, 모든 출입 목적지가 존재함, 모든 에셋·단서·보상 참조가 해석됨, 미지원 정의 버전을 조용히 기본값으로 덮지 않음이다.

제작 상태: artAccepted, collisionApproved, portalValidated, assetReady, logicReady, saveReady, playtestReady 를 별도 기록한다. 이미지가 채택됐다고 나머지를 true 로 두지 않는다.
06→03, 옛 12→12A/12B, 옛 P3→P3A/P3B 별칭은 실제 기존 저장이 있는지 먼저 조사한다. 분할 맵은 옛 위치와 진입 경로를 근거로 안전한 새 스폰에 매핑하며 무조건 첫 방으로 덮지 않는다.

3. 반사광 해석기
근거: 원문 7절. 2D 논리 규칙을 보존한다.

첫 시험은 15 안 광원 1, 거울 1, 수신부 1 로 시작한다. 거울 2 개는 첫 규칙의 가독성이 확인되면 추가한다. 봉인석·문양 잠금·시간 제한·자동 회전은 넣지 않는다. 완료는 실제 연결과 눈에 보이는 수신부 변화로 판정하며 팝업 선택지나 AI 응답으로 대체하지 않는다.

계산 계약
광원은 위치와 단위 방향 d, 활성 조건을 가진다. 거울은 유한 반사 선분, 단위 법선 n, 고정 회전 상태와 활성 조건을 가진다. 수신부는 실제 맞출 유한 영역과 허용 입사 방향 정책을 가진다. 벽·기둥은 광학 높이에서 차단하는 도형이다. 최초 범위는 분기·굴절 없는 단일 광선이며 플레이어와 동행은 빛을 가리지 않는다. 아래 2차원 선분식은 단일 평면 시험용이다. 최신 논의에서는 이를 먼저 구현한다. 원문의 15 높이 적용 요구는 이번 선행조건에서 보류하며 부록에 보존한다.

거울 반사 공식은 d' = d - 2(d·n)n 이다. d 와 n 을 정규화하고 법선은 그림의 손잡이 방향이 아닌 실제 반사면에 수직인 방향이다. 법선 부호가 바뀌어도 양면 거울의 결과는 같다. 단면 청동판을 택하면 반사 가능한 앞면 판정을 먼저 적용하고 뒤면은 차단한다. 해당 선택을 미술과 규칙표에 함께 명시한다.

O0~O3 그림 네 장이 네 개의 서로 다른 광학 결과를 보장하지는 않는다. 평면 거울의 180 도 반전은 양면 모델에서 같은 반사를 만든다. 각 회전 상태에 법선·앞뒷면·그림·허용 방향을 등록하고 모든 합법 입사 방향의 결과표를 검사한다. 미술의 네 방향 수량을 맞추려고 잘못된 물리 규칙을 만들지 않는다.

교차 계산 제안
현재 ray는 p+t·d, t>epsilon이다. 선분은 a+u·(b-a), 0≤u≤1이다. 2차원 외적을 사용하면 분모 cross(d,b-a), t=cross(a-p,b-a)/분모, u=cross(a-p,d)/분모로 후보를 얻는다. 평행·거의 평행·끝점 일치·겹침은 명시적 오차 정책으로 처리한다. 다각형 장애물은 변 교차 중 가장 가까운 양의 t를 취한다. 원형 수신부를 쓰면 해당 ray-circle 교차를 같은 거리 기준에 통합한다.

매 단계에서 가장 가까운 실제 충돌만 선택한다. 수신부 뒤의 벽보다 수신부가 먼저 맞아야 하며, 벽 뒤 수신부를 켜지 않는다. 거리 동률은 안정적인 우선순위와 ID 로 판정하고 장면 검증에서 겹친 광학 표면을 오류로 잡는다. t 가 작은 자기 충돌은 epsilon 이동과 ‘직전 표면의 동일 접점’ 제외로 피하되 직전 거울 전체를 무조건 제외해 정상 재입사를 지우지 않는다.

해석 순서 의사절차
- 모든 수신부의 현재 점등을 false 로 시작한다.
- 광원이 꺼졌으면 선분은 빈 목록으로 끝낸다.
- 현재 ray 의 가장 가까운 후보를 찾고 시작점부터 접점까지 선분을 추가한다.
- 수신부가 맞고 입사 조건이 맞으면 점등하고 종료한다.
- 장애물·비활성 거울·허용되지 않은 뒷면이면 그 접점에서 종료한다.
- 활성 거울이면 반사 방향을 구하고 다음 ray 를 만든다.
- 아무것도 없으면 맵의 광학 경계에서 종료한다. 무한 길이 선을 만들지 않는다.

종료 안전성
처음부터 작가가 승인한 유한 방향 집합과 이에 대해 닫힌 회전 법선 집합을 사용하도록 권장한다. 임의 자유각이 섞이면 이 가정을 다시 설계한다. 방문 상태는 단순 mirrorId 가 아니라 표면 ID·접점·입사 방향·광학 상태 버전의 조합이다. 같은 거울에 다른 위치나 방향으로 도착하는 것은 같은 상태가 아니다.

정규화된 동일 광학 상태가 반복되면 순환으로 종료한다. 부동소수 접점 때문에 반복 검출이 놓치는 경우를 위해 최대 반사 횟수와 총 경로 길이도 유한하게 제한한다. 한도는 장면의 검증된 정답 경로보다 충분히 큰 프로젝트 설정으로 정하고 실제 해법 테스트에 포함한다. 정밀도 양자화를 사용하면 그 단위와 허용 오차를 정의하고, 근사 반복 검출로 중단한 경우 성공으로 처리하지 않고 개발 경고를 남긴다. ‘유한 장치 수이므로 무조건 종료’라는 잘못된 가정을 하지 않는다.

결과는 선분 목록, 충돌·반사 접점, 수신부 점등, 중단 사유다. 퍼즐 성공은 이 결과와 명시한 목표 조건만으로 계산한다. 렌더러는 선분을 그릴 뿐 성공을 판단하지 않는다. 경로와 수신부 결과는 저장 원본이 아닌 파생값이며 로딩·재입장 때 다시 계산한다.

재계산은 회전, 돌 삽입/회수, 광원 on/off, 광학 장애물 변경, 정의 버전 변경, 맵 로드 뒤에만 한다. 카메라 이동은 기존 선분의 화면 투영만 바꾸고 전체 raycast를 매 프레임 다시 하지 않는다. 문이 열려 다른 광학 경로가 바뀌는 경우 같은 명령 처리 안에서 제한된 안정화 단계를 수행하거나, 첫 방에서는 보상 벽감을 주 광학 경로 밖에 두어 의존 순환을 피한다.

4. 운반 봉인석·문·보상
근거: 원문 8절.

16 의 초기 제안은 M1 활성, M2 비활성, S1 비어 있음, K1 접근 가능, R1 꺼짐, 벽감 닫힘이다. K1 은 잠긴 보상 뒤가 아닌 입구에서 접근 가능한 조사 자리에 둔다. S1 에 K1 을 넣으면 M2 가 활성화되고, 거울 연결이 맞으면 R1 이 켜진다. 원천 장치가 항상 켜지는 정의라면 플레이어용 광원 스위치를 임의로 추가하지 않는다.

봉인석 소유권은 하나의 원본으로 관리한다. stoneId 의 location 을 world(맵과 위치), carried(운반 슬롯), socket(socketId) 중 정확히 하나로 둔다. 소켓의 삽입 상태와 바닥 렌더는 이 원본에서 유도하거나 동일 명령에서 일관성을 검증한다. 돌은 일반 판매·소모 인벤토리 품목이 아니다.

각 조작 전제조건
집기: 해당 돌이 접근 가능한 바닥에 있고 운반 가능하며 현재 입력이 유효함.
삽입: 내가 운반 중이고 소켓이 비어 있으며 호환됨. 다른 소켓의 돌을 복제하지 않음.
회수: 해당 소켓에 해당 돌이 있고 운반할 수 있으며 문 닫힘으로 갇히지 않음.
내려놓기: 허용 안전 지점일 때만. 자유 드래그로 벽·출구·도달 불가 영역에 버리지 않음.
회수 복구: 해당 퍼즐의 지정 회수 위치 또는 초기화 계약을 사용하며 다른 맵의 돌을 가져오지 않음.

첫 운반 규칙은 유적 범위를 넘어 돌을 가지고 나가지 않도록 권장한다. 나갈 때 원래 유적 상태에 보관하거나 지정 복구 위치로 돌려놓는 정책 중 하나를 UI로 알린다. 실제로 ‘운반 중 상태 유지’를 채택하면 다른 채팅·유적의 슬롯과 구별하고 맵 밖에서 삽입/판매가 불가능해야 한다. 정책은 제작 전에 확정하고 소유권 불변식을 유지한다.

불변식은 각 돌에 대해 world 수 + carried 수 + socket 수 = 1 이다. 각 소켓은 0 또는 1 개의 호환 돌만 가진다. 이동 명령 실패·연타·저장 재시도·맵 종료 때도 이 수가 바뀌지 않는다. 17 의 두 돌 재배치는 한 돌 규칙과 회수 안전성을 먼저 검증한 뒤 추가한다.

문 상태는 최소한 잠금 조건, 현재 개방, 완료 후 영구 해제를 구분한다. 가동 문은 논리 개방과 충돌 개방을 같은 전이로 바꾼다. 애니메이션은 표현이며 프레임 중간에 충돌이 임의로 풀리지 않는다. 연출이 끝나지 않아도 재입장 시 안정 상태를 복원할 수 있어야 한다.

16 벽감은 최초 해결 후 열린 상태를 유지하는 안을 권장한다. 현재 R1 이 꺼져도 solvedEver 는 남고, 이미 열린 벽감과 받은 보상은 되돌아가지 않는다. 첫 해결 전에는 입력에 따라 R1 점등이 변하지만 ‘보상 수령’은 별도 상호작용이다. 벽감 그림은 닫힘, 열림-유물 있음, 열림-비어 있음 세 결과와 일치해야 한다.

고유 보상은 rewardId 의 수령 여부와 유물 소유를 같은 채팅 저장 스냅샷에서 갱신한다. 이미 수령했다면 재호출은 무변경 성공으로 처리한다. 보상 애니메이션 완료 콜백이나 UI 버튼 비활성 여부에만 중복 방지를 의존하지 않는다. 인벤토리 실패·용량 제한이 있다면 먼저 처리 가능한지 검사하거나 보상 대기 상태로 유지한다. 지급 실패인데 수령 표시만 true 로 만들지 않는다.

5. 문양·단서·풀이 가능성
근거: 원문 9절.

09 는 문양 입문, 13 은 기록 비교 심화, 14 는 익힌 규칙 응용이다. 19 는 관찰과 회전의 응용이며 첫 구현에 천체 시뮬레이션을 추가하지 않는다. 정답 배열과 허용 동작은 작가가 정한 데이터이며 AI 가 세션마다 임의 생성하거나 맞았다고 판정하지 않는다.

단서 정의에는 clueId, 실제 조사 위치, 기록 문장/도해, 참조 규칙, 공개 조건, 확대 자료를 둔다. 정답 정의에는 glyphId와 순서·방향·동치해 허용 범위를 둔다. ‘보여 주는 문양’과 ‘해석하는 문양 ID’가 같은 자료를 참조하게 해 Astra 그림 교체 뒤 의미가 뒤바뀌지 않도록 한다. 정답표는 개발 자료로 분리하고 배경에 번호와 풀이 화살표를 박지 않는다.

발견한 단서는 퀘스트를 받기 전에도 저장한다. 재진입이나 목표 단계 변경 후 이미 확보한 단서를 다시 조사하도록 강제하지 않는다. 조작은 실패 원인을 관찰할 수 있고 무제한 재시도한다. 힌트는 요청 시 관찰 대상 → 역할 → 다음 행동 순으로 제공한다. 마지막 구체 힌트도 검증된 해법 데이터를 사용하고 AI 가 장치 상태를 바꾸지 않는다.

물리 맵 그래프와 정보 의존 그래프를 별도로 검사한다. 18 의 기록을 얻는 데 16 완료가 필요하고 16 을 푸는 데 18 이 필요하면 순환 잠금이다. 17 의 소켓 기본 사용법은 기록고 밖에서 배울 수 있어야 한다. 16 의 필수 정보는 16 을 해결하지 않고 접근 가능해야 하며 토트 신전 미구현에 의존하지 않는다.

작가가 의도한 정답 하나를 실행해 보는 것으로 검증을 끝내지 않는다. 작은 유한 상태 공간에서는 초기 상태에서 합법 조작을 탐색해 해결 상태 도달, 보상 접근, 귀환 가능을 검사한다. 필수 도구 없이·동행 없이·단서를 먼저 읽고·다른 순서로 방문한 경우도 시험한다. 풀이가 여러 개면 허용되는 해법과 의도하지 않은 지름길을 구분한다.

6. 상태 전이·초기화
근거: 원문 10절.

입력 → 명령 검증 → 새 원본 상태 계산 → 파생 광선·문 조건 계산 → 불변식 검사 → 저장 → 화면과 사실 갱신의 경계를 명확히 한다. 실제 저장 전략에 따라 화면을 먼저 바꾸는 낙관적 방식은 가능하나, 실패했을 때 저장되지 않은 상태임을 표시하고 복구 경로를 가져야 한다.

명령 예시는 rotateMirror, pickStone, insertStone, removeStone, setGlyph, inspectClue, claimReward, resetPuzzle 이다. 이름은 제안이다. 명령에는 chatKey, mapId, puzzleId, expectedRevision, commandId 를 전달해 다른 맵의 버튼이나 오래된 콜백을 거부한다. 같은 commandId 재실행은 멱등으로 처리하며 화면의 연속 탭은 개별 합법 명령인지 중복 요청인지 분리한다.

권장 원본 필드: definitionVersion, revision, mirrorOrientations, stoneLocations, glyphSelections, inspectedClues, solvedEver, rewardClaims. 현재 receiverOn, 광선 선분, enabled 장치 집합은 재계산한다. 영구 개방과 순수 현재 조건 개방은 서로 다른 필드나 정책으로 표현한다.

초기화는 현재 퍼즐의 조작 상태와 돌 위치를 검증된 초기값으로 되돌린다. 이미 읽은 단서, 최초 완료, 보상 수령, 일지, 유물, 퀘스트 결론은 보존한다. 이동 중·회전 중 애니메이션과 이전 명령 콜백은 폐기한다. 초기화 뒤 플레이어가 닫힌 문 안에 있지 않도록 검사하고 필요하면 방 내부 안전점으로 옮긴다.

직전 조작 되돌리기는 첫 범위 필수가 아니다. 제공한다면 보상 수령이나 지도 전환을 넘어 외부 인벤토리까지 되돌리는 기능으로 확장하지 않는다. 장치 상태만 되돌려도 solvedEver·rewardClaims 가 지워지지 않아야 한다.

재입장은 저장된 원본 상태 검증 → 정의 버전 마이그레이션 → 파생값 재계산 → 스폰 안전 검사 → 렌더다. 잘못된 orientation 인덱스나 사라진 소켓 참조가 있으면 임의 성공 상태로 만들지 않는다. 백업을 유지하고 장치만 안전 복구하되 보상과 고유 소유품은 손상시키지 않는다.

7. 채팅별 저장·마이그레이션
근거: 원문 11절.

원문의 과거 조사에 기록된 저장 경로는 src/core/state.js의 ctx().chatMetadata[MODULE]와 ctx().saveMetadata()다. 이 API에 데이터베이스 트랜잭션, compare-and-swap, 디스크 fsync가 있다고 가정하면 안 된다. 지원 범위를 실제 실행 환경에서 확인해야 한다. 아래는 보장 수준을 과장하지 않는 논리적 저장 단위 제안이다.

한 채팅의 퍼즐 완료, 고유 유물 추가, rewardClaims, 관련 영구 문, 일지 원천 사실을 하나의 새 스냅샷으로 만들어 한 저장 요청으로 반영한다. 여러 저장 호출 사이에 ‘먼저 유물 추가, 나중에 수령 표시’를 분리하지 않는다. 기존 저장 엔트리에 통합하고 퍼즐만 별도 localStorage 로 저장해 서로 다른 복구 시점을 만들지 않는다.

채팅별 직렬 저장 큐와 revision 을 두어 느린 이전 저장이 최신 상태를 덮지 않게 한다. 전역 저장 함수가 실행 시점의 활성 ctx()를 읽는 구조라면, 큐에 들어갈 때 캡처한 소유 채팅과 실행 시점 채팅을 대조한다. 가능하면 명시적 대상 채팅 저장 어댑터를 제공하고, 지원되지 않으면 전환 직전에 flush 하는 방법과 실패 안내를 검증한다. 활성 B 의 metadata 에 A 스냅샷을 넣는 우회는 금지한다.

채팅 A 에서 에셋 요청·힌트 요청·지연 상호작용·저장 시작 후 B 로 바꾼 경우, 각 작업은 A 의 chatKey 와 sessionGeneration 을 가진다. 완료 시 현재 채팅·맵·요청 세대를 비교하고 맞지 않으면 화면·게임 상태·RP 를 변경하지 않는다. 취소 가능한 요청은 abort 하고, 취소할 수 없는 요청도 stale 결과를 무시한다. 공유 이미지 캐시는 가능하지만 선택 상태·돌·진도는 공유하지 않는다.

저장 실패는 성공 토스트로 숨기지 않는다. 아직 메모리에만 반영된 변경을 표시하고 재시도할 수 있게 한다. 미저장 보상 연출을 반복 지급으로 해석하지 않도록 rewardId 와 작업 상태를 보존한다. 재시도 중에도 같은 채팅 revision 을 확인한다. 앱 종료 직전 비동기 저장 완료를 무조건 보장한다고 말하지 않는다.

버전 관리
과거 조사 시점에는 STATE_VERSION=12였다. 현재 값으로 단정하지 않는다. 새 버전 번호는 구현 시점의 main을 다시 확인한 뒤 정하며 다른 변경과 충돌하지 않는다. 전체 저장 schemaVersion과 퍼즐 definitionVersion을 분리한다. private STEPS의 순차 변환, freshState와 fill의 객체/배열 초기화 목록까지 함께 갱신한다. 원문의 과거 조사에서 s.duat는 카드 원정 상태였다. 현재 용도를 재확인하고 기존 상태 위에 신규 공간 퍼즐 상태를 덮어쓰지 않는다.

마이그레이션 순서
1) 원본 저장을 파괴하지 않은 복구 가능한 백업/내보내기 경로를 확보하고 실제 지원을 시험한다.
2) 사본에서 구버전 → 다음 버전 순차 변환을 수행한다. 버전마다 재실행 안전성을 검사한다.
3) 옛 mapId → 새 의미 ID, 폐지된 장치, 이동 위치, 고유 보상을 명시적 매핑으로 변환한다.
4) 참조·소유권·완료·보상 불변식 검사 후 새 버전 저장을 적용한다.
5) 실패하면 원본을 유지하고 실패 정보를 보여 준다. 깨진 사본으로 원본을 덮지 않는다.

백업을 동일 저장 덩어리 안에만 넣으면 저장 전체 손상에 대한 독립 백업이 아님을 명시한다. 저장 용량과 플랫폼 내보내기/복구 지원을 확인하고 적절한 보관 수를 정한다. 미래 버전 저장을 옛 코드가 읽을 때 자동 다운그레이드하거나 새 필드를 삭제하지 않는다.

과거 저장을 사용자가 직접 복원하면 그 시점 이후 보상과 소유품도 함께 돌아가는 것이 스냅샷 의미다. 별도 권위 서버나 단조 증가 원장이 없는 로컬 저장에서 임의 과거 백업 복원까지 절대적인 중복 수령 방지를 약속하지 않는다. 정상 실행·재시도·동일 스냅샷 복원 안의 멱등 보장과, 수동 롤백의 범위를 구분한다. 인벤토리만 새것이고 퍼즐만 옛것인 혼합 복구는 피한다.

8. 상자·발견 장치·환경 보상
근거: 원문 17절.

01 원판
닫힘/입구열림 두 원본은 같은 맵 상태다. 열림 때 원판이 오른쪽으로 움직이고 왼쪽 좁은 계단이 보인다. 클릭 영역·발 통과·19 포털이 같은 상태를 보게 한다. 닫힌 그림을 가림층에서 다시 그려 계단이 사라지지 않게 한다. 재입장·세이브 복구 후 개방 유지.

9-2. 입력·접근성

장치를 선택한 뒤 가능한 행동만 큰 버튼으로 제공한다. 터치 드래그와 정밀 각도 조절은 필수가 아니다. 겹친 장치는 선택 목록, 작은 단서는 조사 확대본을 사용한다. 멀리 있는 장치를 눌렀을 때 접근 이동인지 설명만 보는지 기존 조작과 일관되게 정하고, 벽을 뚫고 조작하지 않게 접근점을 검사한다.

캔버스 오브젝트는 키보드로 순회 가능한 상호작용 목록과 텍스트 상태를 함께 제공한다. 선택 포커스, 회전·집기·삽입·회수·닫기 동작, 잠금 이유를 표시한다. 색에만 의존하지 않는 수신부 문양, 비활성 핀, 빈/삽입 소켓 표현을 사용한다. 효과 감소 모드에서도 광선 방향과 성공 여부를 읽을 수 있어야 한다. 조작 후 상태 변화는 과도한 반복 없이 텍스트로 알린다.

한 번의 탭을 canvas 와 DOM 이 중복 처리하지 않도록 전파·pointer capture·취소를 다룬다. 선택한 오브젝트가 맵 변경·획득으로 사라지면 메뉴를 닫고 stale 핸들러를 무효화한다. 앱 백그라운드, pointercancel, 패널 닫기에서 이동키나 드래그가 눌린 채 남지 않게 한다.

9-3. 좌표·장치 접점

3/4 그림이라고 기존 엔진이 등각 타일 좌표를 쓴다고 가정하지 않는다. 기존 배경 평면 픽셀 좌표가 월드 좌표라면 이를 유지할 수 있다. 논리 지면 좌표와 미술 투영 좌표를 분리할 필요가 확인될 때만 투영 어댑터를 추가한다.

명시할 좌표 공간은 논리 지면, 배경 이미지, 카메라 적용 후 화면, CSS 입력, 장치 로컬 좌표다. 화면변환을 공통 함수 한 곳에 두고 렌더와 히트테스트가 같은 변환과 역변환을 사용하게 한다. 화면 좌표 = 카메라 변환 × 지면 투영 × 월드 좌표라는 계약을 정하되 실제 행렬·축 방향은 기존 코드 조사에 따른다.

포인터는 캔버스 bounding rect 와 CSS 크기에서 출발해 실제 드로잉 크기 비율을 적용하고, 카메라·투영 역변환으로 옮긴다. devicePixelRatio 를 두 번 곱하거나 확대율을 렌더에만 적용하지 않는다. 창 크기·모바일 회전·브라우저 확대·패널 너비 변경 때 변환을 갱신한다. 장치 선택 화면 영역도 함께 갱신한다.

오브젝트에는 발 기준점, 그림 피벗, 회전축, 광선 접점, 이동 충돌 도형, 선택 도형을 각각 둔다. 투명 PNG 테두리에서 자동으로 발과 충돌을 추측하지 않는다. 반사판 머리 회전은 고정 받침·기둥 그림자까지 같이 돌리지 않는다.

이동 충돌, 광선 차단, 전경 가림은 세 종류다. 발목 높이 받침이 보행은 막아도 광학 높이의 빛은 통과할 수 있고, 높은 기둥은 둘 다 막을 수 있다. 반투명 먼지 연출은 이동이나 광선 규칙을 바꾸지 않는다. 각각의 도형과 높이 정책을 명시하고 하나의 이미지 알파 마스크를 세 용도로 공용하지 않는다.

9-4. 월드 문·운반석의 안전
- 닫히는 문이나 소켓 회수로 충돌이 바뀌면 플레이어 발 도형과의 겹침을 검사한다. 문턱 안에 있으면 닫힘 적용을 안전하게 유예하거나 조작을 설명과 함께 막는다.
- 저장 위치가 지형 밖이면 해당 입구의 안전 스폰으로 복구하고 이유를 개발 로그에 남긴다.
- 문 개방·충돌·장치 상태를 같은 갱신 단위로 적용한다. 입구 트리거를 벗어나기 전까지 재진입을 무장하지 않는다.
- 이동/조사/오버레이 닫기 터치가 포털 진입에도 중복 전달되지 않게 한다.
- 로딩 실패·앱 종료·뒤로 가기·채팅 전환 후 입력 잠금이 남지 않게 소유 토큰별 해제를 보장한다. 오래된 완료가 새 잠금을 풀 수 없어야 한다.
- 사용자의 정밀 수동 충돌 경계를 보존한다. 자동 추론·큰 사각형·과도한 단순화로 교체하지 않는다.
- 동적 문·벽감·운반석은 승인 정적 마스크 위 별도 blocker로 둔다. 모든 이동 소비자와 캐시를 같이 갱신한다.
- 경계가 어긋나면 원본을 다시 그리기 전에 origin/scale/crop/DPR/카메라 역변환을 검사한다.

9-5. 렌더와 성능
- 바닥·그림자·발 깊이 정렬·필요한 전경 가림·광선·UI를 구분한다. 모든 광선을 무조건 최상단에 그리지 않는다.

독립된 광학 단위시험은 한 평면에서 시작할 수 있다. 그러나 채택 15 수신부는 상단 뒷단에 있다. 실제 15 적용은 높이와 반사면을 표현하는 모델(필요시 3 차원 광학 좌표+화면 투영)을 먼저 검증한다. 높은 수신부를 아래로 옮기거나 높이 차이를 선 그림으로만 속이지 않는다. 각 장치의 접점·광학 높이·화면 투영은 같은 정의를 따른다. 그림 접점을 예쁘게 맞추려고 선분 중간을 임의로 구부리지 않는다. 천장 구멍의 분위기 햇빛은 논리 광원 출구와 구분한다.
