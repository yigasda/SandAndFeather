### 주제를 몹 디자인으로 바꾸는 법

**장소의 소재 → 몸이 되는 형태 → 움직임의 원인 → 공격 행동 → 작은 크기에서 읽을 특징** 순으로 생각한다. 이름이나 장식만 먼저 붙이지 않는다.

- 항아리: 토기 자체가 몸. 내부 존재가 뚜껑을 밀고 몸통을 띄운다. 기울임·뚜껑 틈·봉인천의 반응으로 생명감을 만든다. 팔다리·눈·입은 필요 없다. ‘몹답게’라는 지시를 무조건 사람 팔다리 추가로 해석하지 않는다.
- 방패병: 큰 방패가 실루엣을 지배하고 빈 두건과 짧은 발이 뒤에서 움직인다. 막기→몸을 당기기→방패째 돌진이라는 행동이 외형과 연결된다. 손에 검을 추가하거나 전신 갑옷 병사로 확대하지 않는다.
- 이집트 분위기는 색만으로 만들지 않는다. 유럽식 철투구·원형 보스 방패·금속 장화는 반려되었다. 둥근 윗부분/곧은 바닥의 긴 가죽 방패, 해진 아마포, 줄무늬 머릿수건, 봉인끈과 석재처럼 형태·재료·결합 방식으로 표현한다. 이것은 게임 디자인 지침이며 역사적 복원 정확성 주장과는 별개다.
- 맵의 역할과 맞춘다. 지상·유적·지하에서 어떤 소재와 행동이 자연스러운지 [사막 통합 문서](ASTRA-DESERT-05-20-GUIDE.md)로 확인한다. 휴식·보상방에 전투를 임의 추가하지 않는다. 출현 맵·능력치·필수 전투 여부는 그림 채택과 별도 결정이다.

### 같은 주제에서 시안마다 무엇을 바꿀까

고정할 것: **역할, 화풍/도트 밀도, 시점, 대략적인 크기, 조명, 기본 자세.** 비교할 것은 디자인이다. 시안마다 아래 항목 중 적어도 두세 가지를 실질적으로 다르게 잡되 새 수치 규칙처럼 강제하지 않는다.

| 차이 축 | 실제 방패병 예 |
|---|---|
| 큰 실루엣·구조 | 둥근 윗부분의 긴 방패 / 각진 목제 방패 / 위가 좁고 아래가 넓은 깨진 석판 |
| 몸·방어구 재질 | 수선한 가죽 / 칠한 목재와 청동 / 봉인띠로 묶은 돌 |
| 머리와 천 | 해진 밝은 두건 / 줄무늬 머릿수건 / 어두운 빈 두건 |
| 특징 하나 | 굵은 수선 바느질 / 연꽃 장식 / 두 봉인띠와 작은 점토 봉인 |
| 소재에 따른 팔레트 | 붉은 가죽·크림 / 짙은 파랑·황토 / 회갈색 돌·어두운 천 |

색만 바꾸기, 같은 장비에 포즈만 바꾸기, 장식 하나 추가하기는 디자인 3안으로 충분하지 않다. 반대로 시안마다 도트 밀도·카메라·품질까지 바꿔 비교를 어렵게 하지 않는다. 사용자가 여러 안을 채택하면 같은 역할·동작의 계열 변형으로 묶을 수 있다. **가죽형과 봉인석판형은 같은 방패 수호병 계열**이며 임의로 일반/엘리트·상하위 등급을 정하지 않는다. 가운데 연꽃 목제형은 미채택이다.

### 외형에서 10모션으로 연결하기

#### 고정 10칸 순서 — 최신 사용자 지시

앞으로 모든 몹의 기본 모션 시트는 **2행×5칸**, 각 행은 왼쪽부터 읽는다. **대기0·1·2, 준비0·1, 피격, 소멸의 슬롯과 프레임 수는 공통**이다. ‘동일’은 순서·역할·프레임 수가 같다는 뜻이며, 실제 자세는 각 몹의 몸 구조에 맞춘다.

| 행 | 1열 | 2열 | 3열 | 4열 | 5열 |
|---|---|---|---|---|---|
| 위 | 대기0 | 대기1 | 대기2 | 특수 상태: 방어 또는 휴면 등 | 준비0 |
| 아래 | 준비1 | 공격 계열0 | 공격 계열1 | 피격 | 소멸 |

- **4번 칸:** 방어가 더 보편적인 선택이다. 몹의 구조·행동을 보고 방어, 휴면 등 가장 자연스러운 상태를 아스트라가 결정한다. 항아리처럼 닫히고 바닥에 내려앉는 상태가 어울리면 휴면, 버티거나 막는 구조면 방어로 잡는다. 매번 사용자에게 선택을 되묻지 않는다.
- **7·8번 칸:** 공격·돌진·내려찍기 등 이름과 동작은 몹의 구성에 맞춰 아스트라가 결정한다. 모두 **같은 공격 계열의 0·1 두 프레임**이다. 돌진·내려찍기를 별도 슬롯으로 추가하지 않는다.
- **준비는 항상 5·6번의 0·1 두 칸.** 방어/휴면을 빼고 준비를 세 칸으로 늘리지 않는다. 대기 세 칸도 유지한다.
- 피격은 살아 있는 충격 반응, 소멸은 활동 종료를 읽게 한다. 소멸의 파손·빛 꺼짐 등 구체적 표현은 몹과 채택 기준에 맞춘다.
- 제작 전 이번 몹에 선택한 4번 상태와 공격 종류를 짧게 알리고 진행한다. 사용자 별도 지시가 있으면 그 지시가 우선한다.

예시: 항아리 = 위 `대기0 / 대기1 / 대기2 / 휴면 / 준비0`, 아래 `준비1 / 공격0 / 공격1 / 피격 / 소멸`. 방패병 = 같은 배열에서 `방어`, `돌진0·1`. 걸음 비석 = 같은 배열에서 `방어`, `내려찍기0·1`.

다음 실제 채택 사례는 이 고정 배열을 몹별로 표현하는 참고다.

사용자는 한 장씩 만든 항아리 모션의 그림체 차이를 지적했다. **한 번에 10칸을 만들고 그 안에서 외형·색·픽셀 크기를 통일하는 방식**이 현재 선호다. 호출 수가 줄어드는 방식이지 일정 할당량 절감률을 보장하는 것은 아니다.

| 칸 | 항아리 채택 시트 | 방패병 두 종류의 채택 시트 |
|---|---|---|
| 1–3 | 대기0·1·2: 몸통 부유·작은 기울임, 뚜껑 간격·천의 지연 반응 | 대기0·1·2: 체중 이동, 두건 높이·방패 각도의 작은 변화 |
| 4 | 휴면: 바닥에 붙고 뚜껑 닫힘 | 방어: 방패 뒤로 숙이고 발을 벌려 버팀 |
| 5–6 | 준비0·1: 몸을 당기고 뚜껑 간격을 좁힘 | 준비0·1: 방패와 몸을 뒤로 당겨 힘을 모음 |
| 7–8 | 공격0·1: 몸통째 앞으로 튀어나감, 뚜껑과 천이 뒤따름 | 돌진0·1: 앞으로 딛고 방패를 밀어 충돌 |
| 9 | 생존 피격 의도. 실제 시트에는 파편이 생긴 한계가 남음 | 살아 있는 비틀림·방패 어긋남, 파손 없음 |
| 10 | 큰 토기 조각으로 분리되며 기운이 사라짐 | 온전한 방패가 눕고 빈 두건·천이 주저앉음 |

고대장치 원본은 **2종 × idle/prepare/attack/hit/disappear**다. 사용자 사진의 8–10번은 고리형 공격·피격·소멸이지 대기 연속 프레임이 아니다. 준비=모으기, 공격=벌리기, 피격=생존 비틀림, 소멸=분리·핵 꺼짐이라는 구성만 확인했고, 항아리 도트 표현은 이미 만든 항아리를 유지했다. 고대장치에 없는 제작 프롬프트를 만들어서 ‘실제 원문’이라고 하지 않는다.

다른 디자인에 같은 모션을 옮길 때는 **참고1=외형, 참고2=동작 시트**로 역할을 나눈다. 봉인 방패병 제작이 이 방식의 실제 성공 사례다. 동작 참고의 가죽·테두리·수선 무늬가 새 석판에 섞이지 않게 명시한다.

### 프롬프트는 이렇게 연결한다

**새 몹 제작 시 기존 채택 몹의 실제 프롬프트를 먼저 읽고, 그 구성 방식과 작화 지시를 재사용한다. 기존 몹의 디자인을 참고해 새 몹에 옮기라는 뜻이 아니다.**

- 재사용할 것: 출력 형식 → 참고 자료의 역할 → 새 몹의 몸 구조와 살아 움직이는 방식 → 시점·도트 표현 → 시안별 차이 또는 모션 순서 → 해당 작업의 제외 사항 순으로 구체화하는 방식. 채택본의 도트 덩어리·윤곽·내부 명암 밀도와 명확한 행동 묘사를 유지한다.
- 새로 설계할 것: 몸체·실루엣·재질·팔레트·장식·생명감의 원리·공격 방식. 기존 항아리의 토기·봉인천·밀랍, 방패병의 두건·방패, 고대장치의 금장·청록 보석 등을 새 몹의 기본 외형으로 복사하지 않는다. 소재가 새 주제에 자연스럽게 필요하면 독립적으로 선택하되 기존 디자인의 변형에 머무르지 않는다.
- 새 몹에 채택 PNG를 입력할 때는 **‘도트 표현만 참고; 외형·색·장식은 가져오지 않음’**을 프롬프트에 명시한다. 프롬프트 형식을 재사용한다며 이전 몹의 신체 조건이나 금지 사항을 통째로 붙이지 않는다. 팔다리 유무 등은 새 몹 구조로 판단한다.
- **이미 채택한 같은 몹의 모션·수정은 예외:** 해당 몹의 외형 원본을 정확히 유지한다. 다른 몹의 시트가 동작 참고라면 그 이미지에서는 동작·순서만 가져온다. 이 규칙을 외형 보존 지시와 혼동하지 않는다.


실제 전문은 위 링크를 읽는다. 아래는 새 작업용 조립 순서이며 과거 호출 원문이 아니다.

```text
OUTPUT: one sheet, [3 design variants OR 2 rows x 5 motion frames], transparent PNG.
REFERENCE AUTHORITY: reference 1 controls [design / pixel rendering];
reference 2 controls [poses / frame order] ONLY. Explicitly exclude borrowed design/materials.
IDENTITY: [body silhouette, main material, head/limbs if applicable, 2-3 characteristic parts].
STYLE LOCK: reference-level pixel-cluster density, stepped INTERNAL shading,
consistent overhead three-quarter camera, light and physical body scale.
DESIGN VARIANTS: same stance/camera; each option has a different silhouette/material/structure.
OR MOTION CELLS: list every cell in reading order; say what actually moves and what stays rigid.
DELIVERY: full silhouettes, equal cells, generous transparent gutters, no text/grid/scenery.
EXCLUSIONS: brief task-specific failure prevention, not unrelated bans from another creature.
```

재질 잔묘사를 늘리는 것과 도트 밀도를 유지하는 것은 다르다. 기존 몹의 충분한 색면 정보를 남기되 미세한 흠집과 그라데이션을 추가하지 않는다.

**실제 저장과 검증:** 도구의 `transparent_background: true`를 지정하고 출력 PNG의 RGBA와 알파를 확인한다. 미리보기가 검게 보여도 검정 배경으로 단정하지 않는다. 생성 결과와 로컬 저장 파일을 확보한 뒤 백업 완료라고 보고한다. 시트는 게임 적용된 애니메이션이 아니다. 칸 추출·프레임별 발/축 기준점·표시 배율·프레임 시간은 별도 작업이다.

**기준 원본을 찾는 순서:** 최신 main → 적 ID/렌더 호출 → 실제 이미지·아틀라스 경로 → 프레임 사각형·기준점·배율 → 화면에 나온 적과 대조. 아틀라스면 정확한 프레임을 추출하고 출처를 기록한다. 끝내 찾지 못하면 ‘기준 미확인’이라고 밝히고 사용자에게 어떤 기존 몹인지 확인한다. 그동안 관련 맵·후보·기록은 정리할 수 있지만, 임의 기준으로 생성부터 반복하지 않는다. 이미 사용자에게 확인받은 원본은 다시 묻지 않는다.

## 2. ‘조금만 섬세하게’의 뜻

- 기존 도트 크기감·큰 신체 비율·윤곽 굵기·명암 단계는 유지한다. 큰 PNG 해상도와 세밀한 도트는 같은 말이 아니다.
- 추가하는 것은 귀 앞뒤 구분, 등과 옆구리의 면, 집게의 벌어짐, 장치의 분리 구조처럼 **게임 크기에서 형태를 읽게 하는 정보**다.
- 털 한 올, 작은 비늘 전부, 촘촘한 균열, 금속 미세 반사, 여러 겹 중간색을 추가하는 것은 목표가 아니다.
- 원본 색을 보지 않고 팔레트를 임의 16색/32색으로 고정하지 않는다. 재질별 밝음·기본·그림자·깊은 접합의 역할을 확인하고, 추가 단계가 꼭 필요한지 판단한다.
- ‘원본보다 20% 자세하게’ 같은 측정 불가능한 수치로 완료를 판단하지 않는다. 실제 크기에서 기존 몹 옆에 놓았을 때 같은 게임으로 보이는지가 기준이다.

## 3. 몹 도트의 구체적인 모양

### 실루엣과 시점

1. 작은 크기에서 종·앞방향·행동이 먼저 읽혀야 한다. 내부 묘사를 가려도 몸·귀·꼬리·집게 같은 특징이 남는다.
2. 실제 필드 카메라에 맞춘 위에서 내려다보는 3/4. 머리 윗면·등·어깨·장치 윗면이 보이고 발은 같은 지면에 닿는다. 정면 눈높이의 동물 삽화로 바꾸지 않는다.
3. 네발 생물은 가까운/먼 다리의 겹침과 접지를 일관되게 한다. 모든 다리를 보여주려고 벌리거나 길이를 바꾸지 않는다.
4. 몹답게 보인다는 이유로 가시·갑옷·붉은 눈을 일괄 추가하지 않는다. 실루엣·자세·행동으로 적의 역할을 읽게 한다.

### 픽셀과 색면

- 윤곽뿐 아니라 내부의 밝음·그림자도 의도적인 픽셀 덩어리로 만든다. 가장자리만 계단지고 내부는 매끈한 일러스트면 실패다.
- 곡선은 일정한 리듬의 계단으로, 면은 서로 연결된 색 덩어리로 표현한다. 무작위 1픽셀 잡음·잘게 찢어진 색점·과도한 디더링을 피한다.
- 윤곽의 중간색 띠·반투명 후광·에어브러시 그라데이션을 최소화한다. 단, 원본을 측정하지 않고 알파를 일괄 이진화해 가는 부품을 훼손하지 않는다.
- 털은 가슴·등·꼬리의 큰 덩어리와 소수 실루엣 돌기로 표현한다. 석재는 윗면/옆면/접합 그림자, 금속은 적은 밝은 면으로 구분한다.
- 원본보다 복잡한 그림을 만든 뒤 축소·샤프닝·포스터라이즈로 도트처럼 보이게 하는 방식을 기본으로 삼지 않는다. 생성 단계부터 형태와 색면을 단순화한다.
- 실제 표시 배율에서 흐려지면 원본·게임 렌더 보간·브라우저 표시를 구별한다. 무조건 더 선명하게 재생성하지 않는다.

### 캔버스와 크기

투명 PNG를 기본으로 하고, 캔버스 크기와 실제 몸체 경계 크기를 별도로 기록한다. 사람용 620×720/1600×720 규칙을 몹에 자동 적용하지 않는다. 먼저 기존 필드몹의 화면 크기를 확인한다. 필드 전투 계획의 ‘하위몹 약 캐릭터 1.1배’는 해당 계획의 값이며 모든 생물에 강제하지 않는다. 상위 몹 위계도 맵의 통로·플레이어 배율과 함께 결정한다.

## 4. 낭비 없는 제작 순서

1. 최신 사용자 요청에서 종·수량·바꿀 부분을 확인한다. 기존 채택본과 반려본을 구분한다.
2. 기준 필드몹·플레이어·해당 맵을 직접 열어 본다. 기준 파일과 그 역할, 사용할 배율을 짧게 기록하고 사용자에게 알린다.
3. 기준 외형 한 장을 먼저 만든다. 사용자가 시안 여러 장을 요청했다면 그 수를 만들되, 공통 화풍을 고정하고 실루엣·형태 차이를 분명하게 한다. 최초 요청 수를 임의로 축소하지 않는다.
4. **단독 원본 + 맵 위 실제 표시 크기 비교본**을 확인한다. 같은 화면에 기존 몹과 플레이어도 놓되 가림 없이 비교한다. 실제 런타임 배율을 못 얻었으면 ‘가정 배율’이라고 표시하고 게임 검증 완료라 하지 않는다.
5. 외형 채택 후 필요한 방향·상태를 정하고, 최신 방식인 한 번의 10칸 시트 생성으로 모션 제작에 들어간다. 외형 반려 중에 공격·피격까지 양산하지 않는다.
6. 반복 반려면 더 긴 프롬프트로 계속 생성하지 말고 기준 이미지·시점·색면·픽셀 크기 중 무엇이 어긋났는지 먼저 확인한다. 사용자 추가 지시가 오면 그 범위로 재개한다.

## 5. 모션 제작은 외형을 고정한 뒤

- 몸 비율·주요 부품 크기·팔레트·광원·픽셀 크기·기준점이 상태마다 일관돼야 한다. 자세 때문에 짧아 보이는 것과 몸을 축소한 것을 구별한다.
- idle: 살아 있는 기본 자세. prepare: 공격 방향·위험을 읽는 예고. attack: 실제 타격 부위가 이동. hit: 생존 상태의 충격 반응. disappear: 소멸/퇴장. 기본 시트의 상태 순서·프레임 수는 위 고정 10칸 규칙을 따른다. 4번 상태와 7·8번 공격 표현만 몹에 맞춰 정하며, 추가 상태·프레임은 별도 사용자 요청이 있을 때 만든다.
- 부유·통째 회전·확대축소는 보조 움직임이지 모든 모션의 대체물이 아니다. 고대장치의 몸체 분리와 생물의 관절 운동을 같은 방식으로 처리하지 않는다.
- 투사체·큰 먼지·발광은 별도 에셋으로 검토한다. 대기 원본에 큰 효과를 구워 넣어 실루엣을 가리지 않는다.
- 방향 수는 게임이 사용하는 방향과 사용자 요청으로 확정한다. 비대칭 장식·빛·부품이 있는 그림을 무조건 좌우 반전하지 않는다.

## 6. 프롬프트 조립 틀

[맵 공통 프롬프트](ASTRA-MAP-PROMPTS.md)는 수정하지 않는다. 그 문서는 배경용이다. 몹에는 시점·지역 색 조화만 가져오고 ‘전체맵’, 건축 디테일, 배경 밀도를 이식하지 않는다. 아래 대괄호는 실제 확인한 자료로 채운 뒤 사용한다.

```text
Create ONE production-oriented field enemy sprite, [species / silhouette / pose], transparent background.
Reference 1 is the VERIFIED existing field-enemy sprite and controls pixel-cluster scale,
outline weight, simplification, value-step structure and body proportions appropriate to this species.
The target is ONLY SLIGHTLY more detailed than this reference, not a painted illustration.
Reference 2 is the player scale reference. Reference 3 is the map and controls camera,
light direction and local material colors ONLY, not background-level detail density.
Use the same overhead three-quarter gameplay view; readable top planes and grounded feet.
[Describe a few large silhouette features and the enemy's role.]
Use connected deliberate color clusters and stepped internal shading, not only a jagged outline.
Add only [specific necessary structural details]. Keep fur/stone/metal in broad readable masses.
No strand-by-strand fur, tiny cracks, soft airbrush gradients, antialiasing halos,
photorealistic anatomy rendering, product-render lighting or decorative microtexture.
Maintain [verified canvas / body bounds / pivot / intended displayed size].
No scenery, UI, text or baked large attack effects.
```

서로 다른 생물과 장치에 같은 신체 비율을 강제하지 않는다. 체형은 대상 설계에 맞추고 도트 표현의 기준을 공유한다.

## 7. 전달 전 확인

- 기준 원본과 같은 실제 크기에서 같은 게임의 몹처럼 보이는가? 확대 그림이 예쁜 것만으로 통과시키지 않는다.
- 맵과 시점·빛 방향·발 접지/부유 높이가 맞는가? 몸체와 바닥 그림자는 구분했는가?
- 모래·그늘·어두운 바닥 모두에서 몸과 공격 부위가 읽히는가? 실루엣을 밝은 테두리로 감추지 않았는가?
- 털·금속·균열을 줄여도 종이 읽히는가? 작게 보이는 물체 안에 불필요한 디테일이 몰려 있지 않은가?
- 투명 배경의 밝음/어두움 위에 흰 테두리·잔여 배경이 없는가? 확인 확대는 최근접 보간을 쓰고 원본과 표시용 확대본을 구분한다.
- 모션 단계면 프레임별 몸체 크기·기준점·실루엣 움직임을 비교했는가?

자동 크기·해시 검사와 시각적 화풍 검수는 별개다. 실제 게임 검사는 오푸스가 적용할 때 수행한다. 합성 미리보기만으로 충돌·애니메이션 적용 완료라고 하지 않는다.

## 8. 원본 보존과 전달

- 원본·시안·채택·게임 파생본을 구분한다. 기존 채택 파일을 새 생성 결과로 덮어쓰지 않는다. 수정에는 사용자가 지정한 원본을 사용하며 반복 생성본을 무조건 다음 베이스로 쓰지 않는다.
- 새 PNG 자체를 작업별 폴더에 저장한다. 미채택은 후보로 명시하고 최종 몹 목록에 섞지 않는다. 사용자 채택 때 최종 경로/목록을 갱신하되 이전 원본도 보존한다.
- manifest는 source/reference 경로, 크기·몸체 경계·pivot·배율(확인/가정 구분), 방향·상태, SHA256, 채택 근거, 게임 적용 여부를 담는다. 불명확한 값은 추정 확정하지 않는다.
- 기록은 작업별 공통 프롬프트 하나와 시안별 차이로 간소화한다. 같은 긴 설명을 매 장 복제하지 않는다.
- **PNG 저장 → 필요한 파일만 커밋 → main 푸시 → 원격 커밋과 파일 존재 확인**을 끝낸 뒤 백업 완료라고 말한다. 다른 세션의 작업은 덮어쓰거나 강제 푸시하지 않는다.
- Drive에는 채택본만 올린다. 기존 파일 교체 요청이면 올바른 파일 ID를 확인해 교체하고 목록/메타데이터로 확인한다.
- 아스트라는 그림 제작·원본 보존까지 맡는다. 게임 데이터·렌더·충돌·배포는 별도 요청과 오푸스 적용 절차를 따른다.
