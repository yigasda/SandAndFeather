2. 이 문서는 **기존 게임에 적용할 맵 전용 인수인계**다. 이번 문서 작성 자체는 게임 코드 변경이 아니다. 실제 구현 시에는 기존 기반과 승인된 연결을 재사용하고 확인된 누락 기능만 추가한다. 최신 사용자 문서 정합화 요청에 따라 관련 맵 문서의 현재 안내를 갱신하되 생성 프롬프트 본문은 보존한다.
3. **신전 본선은 02↔15↔T2↔11↔02, 앞뜰 순환은 15↔T1W↔T1E↔T2↔15, 16 접근은 T2↔T3↔16이다.** 문별 대응·T1W-B 두 연결·출입 제외 지점은 [신전 최신 연결 기준](DESERT-TEMPLE-CONNECTIONS.md)을 따른다. 02의 다른 사막 연결은 보존한다. 실제 승인 출입구를 이용하고, 좌표가 아직 이 문서에 없다는 이유로 임의 임시 포털이나 중앙 텔레포트를 만들지 않는다.
4. 사용자 수동 충돌은 이미 존재하는 승인 자료다. **16 빛 우물 승인 충돌 경로는 `사막맵/충돌/16_빛우물.png`이며, 기존 Drive의 `사막맵 충돌` 폴더도 대조한다.** 이 경로는 최신 전달 내용으로 확인된 위치이며 이 문서 작업에서 파일 자체를 재열거나 해시 검증한 결과는 아니다. 원문 부록의 옛 충돌 상태를 현재 상태로 옮기지 않는다. 정확한 경로·변환·배경 버전을 기존 저장소/작업 자료에서 확인하고, 원본을 다시 그리거나 파일 전체를 다시 보내 달라고 하는 것을 기본 대안으로 삼지 않는다.

## 2. 기존 소스 조사와 작업 시작 조건

출처: 원문 L50–L66.

실제 구현을 시작하는 Opus 는 작업 브랜치와 기준 커밋을 먼저 기록한다. 저장소의 AGENTS.md, 실행 방법, 관련 로컬 스킬과 테스트 규칙을 읽는다. 현재 배포와 main 이 같은 상태인지 확인하고, 다른 작업자의 미커밋 변경을 보존한다. 이 문서의 마지막 소스 조사 기록은 특정 시점의 읽기 확인이며 향후 체크아웃과 자동으로 동일하지 않다.

다음 항목을 기존 심볼과 호출 경로까지 추적해 짧은 조사표로 남긴다.
- 맵 등록부, 기존 사막 ID, 배경 이미지 선택, mapId 를 사용하는 전체 소비자.
- 캐릭터 이동 루프, 발 기준점, 충돌, 카메라 오프셋과 확대율, CSS 크기와 캔버스 실제 크기.
- 출입 조건, 목적지 스폰, 이동 완료 처리, 되돌아오기와 텔레포트.
- 조사·채집·낚시·상점 등 기존 인터랙션 진입점과 중복 입력 방지.
- 채팅 선택, 채팅별 게임 상태의 생성·로딩·복사·삭제, 비동기 저장 순서.
- 인벤토리 추가, 퀘스트·일지·가구 상태, 고유 보상과 일반 자원 처리.
- RP 메시지 생성과 사용자 확인 지점, 이벤트 또는 프롬프트가 섞이는 경로.
- 테스트·빌드·패키징 방식, 에셋 다운로드와 캐시의 해제 방식.

재사용은 실제 동작을 확인한 부분에만 적용한다. 기존 함수가 전역 상태를 수정하거나 활성 채팅을 실행 시점에 다시 읽으면, 이름만 맞춰 퍼즐에 붙이지 않는다. 채팅 소유권과 중복 지급을 보장하는 어댑터를 먼저 설계한다. 기존 렌더러 전체 교체나 범용 엔진 도입은 선행 조건이 아니다.

조사 종료 조건은 ‘파일을 봤음’이 아니다. 기존 맵 1 개에서 좌표가 입력 → 이동 → 충돌 → 화면까지 흐르는 경로, 저장 1 건이 채팅 선택 → 로드 → 수정 → 영속화까지 흐르는 경로를 설명할 수 있어야 한다. 기존 기능의 간단한 회귀 시나리오도 저장해 이후 변경과 비교한다.

## 3. 데이터 경계와 고정 식별자

출처: 원문 L68–L92.

다음은 신규 설계 제안이다. 실제 언어·모듈 명명은 저장소 관례에 맞춘다.

정적 정의와 저장 상태를 분리한다.
- 맵 정의: 의미 기반 mapId, 표시명, 지역, 에셋 참조, 논리 경계, 보행 영역, 정적 광선 장애물, 출입구, 오브젝트 배치, 단서 참조, 제작 상태.
- 퍼즐 정의: puzzleId, definitionVersion, 장치와 합법 조작, 초기 상태, 해결 규칙, 완료 유지 정책, 보상 참조, 필수 단서, 개발자 해답 증거.
- 맵 런타임: 로딩 중 이미지·렌더 캐시·선택 대상·광선 선분·입력 잠금. 저장하지 않는 파생 데이터다.
- 채팅별 월드 상태: 방문·발견, 퍼즐 가변 상태, 단서, 통로 개방, 고유 보상 수령, 유물 단계와 전시, 안전 귀환점.

숫자와 T/P 번호는 제작용 표기다. 배열 인덱스나 표시명을 저장 키로 쓰지 않는다. 예시 ‘desert.lightwell’, ‘desert.colonnade’, ‘puzzle.desert.lightwell.main’, ‘device.lightwell.mirror_a’는 제안 ID이며 현재 코드의 실제 ID가 아니다. 한 번 배포한 의미 ID는 정렬·번역·파일명 변경으로 바꾸지 않는다. 여러 맵에서 공용 거울 그림을 쓰더라도 장치 인스턴스 ID는 서로 달라야 한다.

ID 네 층을 혼동하지 않는다.
- assetId 는 재사용 가능한 그림.
- objectId 는 맵 안 한 배치물.
- puzzleId 는 여러 배치물을 묶은 규칙.
- rewardId 는 같은 채팅에서 지급을 한 번만 인정할 고유 권리.

맵 이름이 바뀌면 표시명만 바꾼다. 맵을 합치면 옛 ID 를 별칭으로 남기고 위치·단서·완료·보상을 새 소유 맵에 명시적으로 매핑한다. 기존 사막 방문 하나를 신규 맵 모두 발견한 것으로 변환하지 않는다. 기존 보유품과 완료 보상은 실제 대응 근거를 확인해 보존한다.

현재 34 개 공간의 제작 번호와 의미 ID 를 연결하는 검토용 등록부를 둔다. 필수 검증은 ID 중복 없음, 모든 출입 목적지가 존재함, 모든 에셋·단서·보상 참조가 해석됨, 미지원 정의 버전을 조용히 기본값으로 덮지 않음이다.

추가 정적 정의: speciesId·motionSetId·attackProfileId·spawnId·encounterId·respawnPolicyId 를 분리한다. 몹 한 종의 그림과 맵 속 여러 개체는 같은 ID 가 아니다. 보스 소멸 여부와 고유 보상 수령도 다른 상태다.
제작 상태: artAccepted, collisionApproved, portalValidated, assetReady, logicReady, saveReady, playtestReady 를 별도 기록한다. 이미지가 채택됐다고 나머지를 true 로 두지 않는다.
06→03, 옛 12→12A/12B, 옛 P3→P3A/P3B 별칭은 실제 기존 저장이 있는지 먼저 조사한다. 분할 맵은 옛 위치와 진입 경로를 근거로 안전한 새 스폰에 매핑하며 무조건 첫 방으로 덮지 않는다.

## 7. 맵 전환과 안전한 귀환

출처: 원문 L309–L328.

출입 정의에는 고정 portalId, 목적지 mapId 와 destinationSpawnId, 트리거 도형, 접근 조건, 출입 방식, 화면 안내, 귀환 연결을 둔다. 목적지 스폰에는 발 위치·바라보는 방향·안전 영역·카메라 초기 기준을 둔다. 좌표 수치는 실제 캔버스와 캐릭터 충돌 검사 후 확정한다.

넓은 대형맵 경계는 ‘경계에 도달해 넘어가기’, 문·원판은 ‘접근 후 들어가기’처럼 기존 입력과 어울리게 구분할 수 있다. 어떤 방식이든 조사 터치가 자동 이동으로 바뀌지 않게 한다. 같은 터치가 UI 닫기와 포털 진입에 동시에 전달되지 않아야 한다.

전환 처리 제안
1) 현재 채팅·맵·세대 토큰과 출발 위치를 캡처하고 조건을 검사한다.
2) 진행 중 전환을 한 건으로 제한한다. 이동 입력과 연속 포털 활성화를 잠시 잠근다.
3) 출발 상태 저장을 요청하고 목적지 정의·필수 에셋·상태를 준비한다. 저장 실패 정책을 명시한다.
4) 요청이 여전히 같은 세대에 속하는지 검사한다. 목적지 스폰이 열려 있고 충돌하지 않는지 확인한다.
5) 맵·위치·카메라·충돌·장치 상태를 같은 화면 갱신 단위로 설치한다.
6) 목적지 입구 트리거를 벗어나기 전까지 재진입을 무장하지 않는다. 시간 지연만으로 왕복 루프를 막지 않는다.
7) 진입 사실을 한 번 기록하고 입력을 복구한다. 실패하면 안전한 출발 화면과 설명을 유지한다.

역방향 이동은 상대 맵 중앙으로 순간이동시키는 임시 처리로 끝내지 않는다. 들어온 문에 대응하는 착지점을 사용하고 시선은 입구 밖/실내 진행 쪽으로 맞춘다. 동행은 스폰을 점유해 플레이어를 밀거나 포털을 다시 발동시키지 않도록 비차단 배치 또는 별도 안전 후보점을 쓴다.

닫히는 문, 환경 지형, 소켓 회수로 충돌이 바뀔 때 플레이어 발 도형과의 겹침을 먼저 검사한다. 문턱 안에 있을 때는 닫힘 적용을 안전하게 유예하거나 해당 조작을 설명과 함께 막는다. 이미 지형 밖에 저장된 위치는 해당 입구의 안전 스폰으로 보정하고 이유를 개발 로그에 남긴다. 지도 전체 임의 좌표로 보내지 않는다.

앱 종료·브라우저 뒤로 가기·로딩 실패·대화 전환에서도 전환 잠금이 영구히 남지 않도록 소유 토큰별 해제를 보장한다. 오래된 비동기 완료가 새 전환의 잠금을 풀지 못하게 한다.

## 8. 좌표계·카메라·충돌

출처: 원문 L330–L342.

3/4 그림이라고 기존 엔진이 등각 타일 좌표를 쓴다고 가정하지 않는다. 기존 배경 평면 픽셀 좌표가 월드 좌표라면 이를 유지할 수 있다. 논리 지면 좌표와 미술 투영 좌표를 분리할 필요가 확인될 때만 투영 어댑터를 추가한다.

명시할 좌표 공간은 논리 지면, 배경 이미지, 카메라 적용 후 화면, CSS 입력, 장치 로컬 좌표다. 화면변환을 공통 함수 한 곳에 두고 렌더와 히트테스트가 같은 변환과 역변환을 사용하게 한다. 화면 좌표 = 카메라 변환 × 지면 투영 × 월드 좌표라는 계약을 정하되 실제 행렬·축 방향은 기존 코드 조사에 따른다.

포인터는 캔버스 bounding rect 와 CSS 크기에서 출발해 실제 드로잉 크기 비율을 적용하고, 카메라·투영 역변환으로 옮긴다. devicePixelRatio 를 두 번 곱하거나 확대율을 렌더에만 적용하지 않는다. 창 크기·모바일 회전·브라우저 확대·패널 너비 변경 때 변환을 갱신한다. 장치 선택 화면 영역도 함께 갱신한다.

오브젝트에는 발 기준점, 그림 피벗, 회전축, 광선 접점, 이동 충돌 도형, 선택 도형을 각각 둔다. 투명 PNG 테두리에서 자동으로 발과 충돌을 추측하지 않는다. 반사판 머리 회전은 고정 받침·기둥 그림자까지 같이 돌리지 않는다.

독립된 광학 단위시험은 한 평면에서 시작할 수 있다. 그러나 채택 15 수신부는 상단 뒷단에 있다. 실제 15 적용은 높이와 반사면을 표현하는 모델(필요시 3 차원 광학 좌표+화면 투영)을 먼저 검증한다. 높은 수신부를 아래로 옮기거나 높이 차이를 선 그림으로만 속이지 않는다. 각 장치의 접점·광학 높이·화면 투영은 같은 정의를 따른다. 그림 접점을 예쁘게 맞추려고 선분 중간을 임의로 구부리지 않는다. 천장 구멍의 분위기 햇빛은 논리 광원 출구와 구분한다.

이동 충돌, 광선 차단, 전경 가림은 세 종류다. 발목 높이 받침이 보행은 막아도 광학 높이의 빛은 통과할 수 있고, 높은 기둥은 둘 다 막을 수 있다. 반투명 먼지 연출은 이동이나 광선 규칙을 바꾸지 않는다. 각각의 도형과 높이 정책을 명시하고 하나의 이미지 알파 마스크를 세 용도로 공용하지 않는다.

## 9. 렌더 순서·가림과 Astra 에셋 계약

출처: 원문 L344–L378.

기존 렌더 패스를 확장하되 다음 결과를 보장한다.
- 바닥·고정 배경.
- 바닥에 붙는 표시·그림자·국소 효과.
- 낮은 설치물과 캐릭터 및 장치: 발 깊이와 명시적 안정 순서로 정렬.
- 높이가 있는 장치 머리, 문틀·기둥 앞면 등 필요한 가림 조각.
- 해당 광학 높이의 광선과 접촉 효과: 같은 높이의 가림 규칙 적용.
- 선택·상호작용 안내·접근성 텍스트 등 화면 UI.

이 목록을 무조건 전부 독립 캔버스로 만드는 것은 아니다. 기존 단일 캔버스에서도 정렬된 드로우 명령으로 가능하다. 특히 ‘모든 빛을 맨 위에 그리기’와 ‘모든 전경을 캐릭터 위에 그리기’는 피한다. 광선은 먼저 실제 장애물에서 끝나고, 화면상 겹침은 전경 마스크나 잘린 구간으로 표현한다. 동일 깊이에는 objectId 등 안정적인 타이브레이커를 써 깜빡임을 막는다.

Astra 에게 받는 계약 제안
맵 묶음: 기본 배경, 필요한 투명 전경, 가동 장치 참조, 별도 효과, 검토용 배치도와 상태 합성본, manifest.
에셋 항목: 고정 assetId와 버전, 파일 참조, 실제 크기, 기준점, 회전축·광선 접점, 방향·상태 대응, 가림 정책, 충돌/선택 담당, 재사용 제한, 승인 단계.
장면 배치 항목: objectId, assetId, 월드 위치·상태, 장치 역할, 상호작용 접근점, 광선/보행 도형, 관련 퍼즐·단서·문 참조.

픽셀 크기·출력 해상도·폴더명은 현재 배율과 저장소 규칙을 확인한 뒤 정한다. 아직 없는 파일을 manifest 에 최종 경로로 등록하지 않는다. 같은 상태군은 캔버스 크기와 피벗을 유지하며 작은 돌을 전체맵 크기의 투명 PNG 로 받지 않는다. 검토본은 런타임 assetId 에 포함하지 않는다.

준비 상태 제안
concept: 구도·색 시안. 플레이 적용 승인 아님.
layout_validated: 회색 배치에서 동선·해법·장치 접점 확인.
integration_candidate: 필요한 분리 파일과 metadata가 있어 실제 배율 검수 가능.
approved: 실제 캐릭터·모바일·모든 상태 조합 검수 완료.
retired: 이전 버전. 저장 ID 는 유지하고 에셋 대체 이력 보존.

현재 채택 대형 네 장의 미술 상태는 artAccepted 다. 위 concept 등은 향후 제작 단계용 일반 구분이며 이미 채택된 원화를 시안으로 강등하지 않는다. 별도로 logicalReady, assetReady, saveReady, playtestReady 를 기록해 배경 한 장이 있다는 이유로 맵 전체를 완료 처리하지 않는다. 개발 모드에서는 누락 에셋을 식별 가능한 도형으로 표시할 수 있지만 출시 경로에서 흰 화면이나 조작 불가능한 장면으로 진입시키지 않는다.

장치 대응
P01 받침 / P02 거울 머리 / P03 광원 / P04 수신부는 15 입문부터 사용.
P05 돌 / P06 소켓 / P08 단서 / P10 벽감 / P11 봉인은 원문 16 결합안의 장치 대응이다. 해당 구체 구성은 역사적 의존성이며 현재 최종 승인안으로 강제하지 않는다.

P12 원판은 01·19, P13 발굴은 실제 출토 장소, P14 효과는 공용.

### 10.1 맵과 광학 해석기의 경계

출처: §7 L382–385·410–412. 상세 공식·교차 계산·순환 판정은 원문 §7 L387–408에 위임한다.

- 15의 첫 검증은 광원 1·거울 1·수신부 1부터. 실제 광학 연결과 눈에 보이는 수신부 변화로 확인하며 팝업이나 AI 답변으로 대체하지 않는다. 초기 장면에 새 봉인석·시간 제한·자동 회전을 추가하지 않는다.
- 장면 정의는 광원, 거울 접점/법선, 수신부 영역·입사 조건, 벽·기둥의 광학 높이를 제공한다. 실제 15 수신부 높이를 평면식으로 무시하지 않는다. 플레이어·동행은 첫 광학 범위에서 빛을 가리지 않는다.
- 해석기는 선분·접점·수신부 점등·종료 사유를 돌려주고, 렌더러는 결과를 표현한다. 광선 경로는 영속 원본이 아닌 파생값이며 로드/재입장 때 재계산한다.
- 회전, 삽입/회수, 광원 상태, 광학 장애물, 정의 버전, 맵 로드가 바뀔 때 재계산한다. 카메라만 움직이면 투영만 바꾼다. 문 개방에 의한 광학 의존 순환을 피하거나 제한된 안정화 처리를 검증한다.

### 10.2 운반석·문·보상: 배치와 상태 안전

**과거 의존성:** 다음 M1/M2/S1/K1·소켓 구성은 현재 확정 설계가 아니다. 위치 안전·소유권·퇴로 원칙은 새 승인안에도 적용하되, 이 구성 자체를 되살리지 않는다.

16 의 초기 제안은 M1 활성, M2 비활성, S1 비어 있음, K1 접근 가능, R1 꺼짐, 벽감 닫힘이다. K1 은 잠긴 보상 뒤가 아닌 입구에서 접근 가능한 조사 자리에 둔다. S1 에 K1 을 넣으면 M2 가 활성화되고, 거울 연결이 맞으면 R1 이 켜진다. 원천 장치가 항상 켜지는 정의라면 플레이어용 광원 스위치를 임의로 추가하지 않는다.

봉인석 소유권은 하나의 원본으로 관리한다. stoneId 의 location 을 world(맵과 위치), carried(운반 슬롯), socket(socketId) 중 정확히 하나로 둔다. 소켓의 삽입 상태와 바닥 렌더는 이 원본에서 유도하거나 동일 명령에서 일관성을 검증한다. 돌은 일반 판매·소모 인벤토리 품목이 아니다.

각 조작 전제조건
집기: 해당 돌이 접근 가능한 바닥에 있고 운반 가능하며 현재 입력이 유효함.
삽입: 내가 운반 중이고 소켓이 비어 있으며 호환됨. 다른 소켓의 돌을 복제하지 않음.
회수: 해당 소켓에 해당 돌이 있고 운반할 수 있으며 문 닫힘으로 갇히지 않음.
내려놓기: 허용 안전 지점일 때만. 자유 드래그로 벽·출구·도달 불가 영역에 버리지 않음.
회수 복구: 해당 퍼즐의 지정 회수 위치 또는 초기화 계약을 사용하며 다른 맵의 돌을 가져오지 않음.

첫 운반 규칙은 유적 범위를 넘어 돌을 가지고 나가지 않도록 권장한다. 나갈 때 원래 유적 상태에 보관하거나 지정 복구 위치로 돌려놓는 정책 중 하나를 UI로 알린다. 실제로 ‘운반 중 상태 유지’를 채택하면 다른 채팅·유적의 슬롯과 구별하고 맵 밖에서 삽입/판매가 불가능해야 한다. 정책은 제작 전에 확정하고 소유권 불변식을 유지한다.

불변식은 각 돌에 대해 world 수 + carried 수 + socket 수 = 1 이다. 각 소켓은 0 또는 1 개의 호환 돌만 가진다. 이동 명령 실패·연타·저장 재시도·맵 종료 때도 이 수가 바뀌지 않는다. 17 의 두 돌 재배치는 한 돌 규칙과 회수 안전성을 먼저 검증한 뒤 추가한다.

문 상태는 최소한 잠금 조건, 현재 개방, 완료 후 영구 해제를 구분한다. 가동 문은 논리 개방과 충돌 개방을 같은 전이로 바꾼다. 애니메이션은 표현이며 프레임 중간에 충돌이 임의로 풀리지 않는다. 연출이 끝나지 않아도 재입장 시 안정 상태를 복원할 수 있어야 한다.

고유 보상은 rewardId 의 수령 여부와 유물 소유를 같은 채팅 저장 스냅샷에서 갱신한다. 이미 수령했다면 재호출은 무변경 성공으로 처리한다. 보상 애니메이션 완료 콜백이나 UI 버튼 비활성 여부에만 중복 방지를 의존하지 않는다. 인벤토리 실패·용량 제한이 있다면 먼저 처리 가능한지 검사하거나 보상 대기 상태로 유지한다. 지급 실패인데 수령 표시만 true 로 만들지 않는다.

### 10.3 단서 위치와 순환 잠금 방지

09 는 문양 입문, 13 은 기록 비교 심화, 14 는 익힌 규칙 응용이다. 19 는 관찰과 회전의 응용이며 첫 구현에 천체 시뮬레이션을 추가하지 않는다. 정답 배열과 허용 동작은 작가가 정한 데이터이며 AI 가 세션마다 임의 생성하거나 맞았다고 판정하지 않는다.

단서 정의에는 clueId, 실제 조사 위치, 기록 문장/도해, 참조 규칙, 공개 조건, 확대 자료를 둔다. 정답 정의에는 glyphId와 순서·방향·동치해 허용 범위를 둔다. ‘보여 주는 문양’과 ‘해석하는 문양 ID’가 같은 자료를 참조하게 해 Astra 그림 교체 뒤 의미가 뒤바뀌지 않도록 한다. 정답표는 개발 자료로 분리하고 배경에 번호와 풀이 화살표를 박지 않는다.

발견한 단서는 퀘스트를 받기 전에도 저장한다. 재진입이나 목표 단계 변경 후 이미 확보한 단서를 다시 조사하도록 강제하지 않는다. 조작은 실패 원인을 관찰할 수 있고 무제한 재시도한다. 힌트는 요청 시 관찰 대상 → 역할 → 다음 행동 순으로 제공한다. 마지막 구체 힌트도 검증된 해법 데이터를 사용하고 AI 가 장치 상태를 바꾸지 않는다.

물리 맵 그래프와 정보 의존 그래프를 별도로 검사한다. 18 의 기록을 얻는 데 16 완료가 필요하고 16 을 푸는 데 18 이 필요하면 순환 잠금이다. 17 의 소켓 기본 사용법은 기록고 밖에서 배울 수 있어야 한다. 16 의 필수 정보는 16 을 해결하지 않고 접근 가능해야 하며 토트 신전 미구현에 의존하지 않는다.

작가가 의도한 정답 하나를 실행해 보는 것으로 검증을 끝내지 않는다. 작은 유한 상태 공간에서는 초기 상태에서 합법 조작을 탐색해 해결 상태 도달, 보상 접근, 귀환 가능을 검사한다. 필수 도구 없이·동행 없이·단서를 먼저 읽고·다른 순서로 방문한 경우도 시험한다. 풀이가 여러 개면 허용되는 해법과 의도하지 않은 지름길을 구분한다.

## 11. 결정적 상태 전이·초기화·재입장

출처: 원문 L449–L461.

입력 → 명령 검증 → 새 원본 상태 계산 → 파생 광선·문 조건 계산 → 불변식 검사 → 저장 → 화면과 사실 갱신의 경계를 명확히 한다. 실제 저장 전략에 따라 화면을 먼저 바꾸는 낙관적 방식은 가능하나, 실패했을 때 저장되지 않은 상태임을 표시하고 복구 경로를 가져야 한다.

명령 예시는 rotateMirror, pickStone, insertStone, removeStone, setGlyph, inspectClue, claimReward, resetPuzzle 이다. 이름은 제안이다. 명령에는 chatKey, mapId, puzzleId, expectedRevision, commandId 를 전달해 다른 맵의 버튼이나 오래된 콜백을 거부한다. 같은 commandId 재실행은 멱등으로 처리하며 화면의 연속 탭은 개별 합법 명령인지 중복 요청인지 분리한다.

권장 원본 필드: definitionVersion, revision, mirrorOrientations, stoneLocations, glyphSelections, inspectedClues, solvedEver, rewardClaims. 현재 receiverOn, 광선 선분, enabled 장치 집합은 재계산한다. 영구 개방과 순수 현재 조건 개방은 서로 다른 필드나 정책으로 표현한다.

초기화는 현재 퍼즐의 조작 상태와 돌 위치를 검증된 초기값으로 되돌린다. 이미 읽은 단서, 최초 완료, 보상 수령, 일지, 유물, 퀘스트 결론은 보존한다. 이동 중·회전 중 애니메이션과 이전 명령 콜백은 폐기한다. 초기화 뒤 플레이어가 닫힌 문 안에 있지 않도록 검사하고 필요하면 방 내부 안전점으로 옮긴다.

직전 조작 되돌리기는 첫 범위 필수가 아니다. 제공한다면 보상 수령이나 지도 전환을 넘어 외부 인벤토리까지 되돌리는 기능으로 확장하지 않는다. 장치 상태만 되돌려도 solvedEver·rewardClaims 가 지워지지 않아야 한다.

재입장은 저장된 원본 상태 검증 → 정의 버전 마이그레이션 → 파생값 재계산 → 스폰 안전 검사 → 렌더다. 잘못된 orientation 인덱스나 사라진 소켓 참조가 있으면 임의 성공 상태로 만들지 않는다. 백업을 유지하고 장치만 안전 복구하되 보상과 고유 소유품은 손상시키지 않는다.

## 12. 채팅별 저장·마이그레이션

출처: 원문 L463–L487.

원문 스냅샷에서 확인했던 저장 경로는 src/core/state.js의 ctx().chatMetadata[MODULE]와 ctx().saveMetadata()다. 현재 경로와 지원 범위는 최신 코드에서 재확인한다. 이 API에 데이터베이스 트랜잭션, compare-and-swap, 디스크 fsync가 있다고 가정하면 안 된다. 지원 범위를 실제 실행 환경에서 확인해야 한다. 아래는 보장 수준을 과장하지 않는 논리적 저장 단위 제안이다.

한 채팅의 퍼즐 완료, 고유 유물 추가, rewardClaims, 관련 영구 문, 일지 원천 사실을 하나의 새 스냅샷으로 만들어 한 저장 요청으로 반영한다. 여러 저장 호출 사이에 ‘먼저 유물 추가, 나중에 수령 표시’를 분리하지 않는다. 기존 저장 엔트리에 통합하고 퍼즐만 별도 localStorage 로 저장해 서로 다른 복구 시점을 만들지 않는다.

채팅별 직렬 저장 큐와 revision 을 두어 느린 이전 저장이 최신 상태를 덮지 않게 한다. 전역 저장 함수가 실행 시점의 활성 ctx()를 읽는 구조라면, 큐에 들어갈 때 캡처한 소유 채팅과 실행 시점 채팅을 대조한다. 가능하면 명시적 대상 채팅 저장 어댑터를 제공하고, 지원되지 않으면 전환 직전에 flush 하는 방법과 실패 안내를 검증한다. 활성 B 의 metadata 에 A 스냅샷을 넣는 우회는 금지한다.

채팅 A 에서 에셋 요청·힌트 요청·지연 상호작용·저장 시작 후 B 로 바꾼 경우, 각 작업은 A 의 chatKey 와 sessionGeneration 을 가진다. 완료 시 현재 채팅·맵·요청 세대를 비교하고 맞지 않으면 화면·게임 상태·RP 를 변경하지 않는다. 취소 가능한 요청은 abort 하고, 취소할 수 없는 요청도 stale 결과를 무시한다. 공유 이미지 캐시는 가능하지만 선택 상태·돌·진도는 공유하지 않는다.

저장 실패는 성공 토스트로 숨기지 않는다. 아직 메모리에만 반영된 변경을 표시하고 재시도할 수 있게 한다. 미저장 보상 연출을 반복 지급으로 해석하지 않도록 rewardId 와 작업 상태를 보존한다. 재시도 중에도 같은 채팅 revision 을 확인한다. 앱 종료 직전 비동기 저장 완료를 무조건 보장한다고 말하지 않는다.

버전 관리
원문 당시 STATE_VERSION=12였다는 역사 기록이며 현재 버전이라는 뜻은 아니다. 새 버전 번호는 구현 시점의 main을 다시 확인한 뒤 정하며 다른 변경과 충돌하지 않는다. 전체 저장 schemaVersion과 퍼즐 definitionVersion을 분리한다. private STEPS의 순차 변환, freshState와 fill의 객체/배열 초기화 목록까지 함께 갱신한다. 기존 s.duat는 카드 원정 상태이므로 그 자리에 신규 공간 퍼즐 상태를 덮어쓰지 않는다.

마이그레이션 순서
1) 원본 저장을 파괴하지 않은 복구 가능한 백업/내보내기 경로를 확보하고 실제 지원을 시험한다.
2) 사본에서 구버전 → 다음 버전 순차 변환을 수행한다. 버전마다 재실행 안전성을 검사한다.
3) 옛 mapId → 새 의미 ID, 폐지된 장치, 이동 위치, 고유 보상을 명시적 매핑으로 변환한다.
4) 참조·소유권·완료·보상 불변식 검사 후 새 버전 저장을 적용한다.
5) 실패하면 원본을 유지하고 실패 정보를 보여 준다. 깨진 사본으로 원본을 덮지 않는다.

백업을 동일 저장 덩어리 안에만 넣으면 저장 전체 손상에 대한 독립 백업이 아님을 명시한다. 저장 용량과 플랫폼 내보내기/복구 지원을 확인하고 적절한 보관 수를 정한다. 미래 버전 저장을 옛 코드가 읽을 때 자동 다운그레이드하거나 새 필드를 삭제하지 않는다.

과거 저장을 사용자가 직접 복원하면 그 시점 이후 보상과 소유품도 함께 돌아가는 것이 스냅샷 의미다. 별도 권위 서버나 단조 증가 원장이 없는 로컬 저장에서 임의 과거 백업 복원까지 절대적인 중복 수령 방지를 약속하지 않는다. 정상 실행·재시도·동일 스냅샷 복원 안의 멱등 보장과, 수동 롤백의 범위를 구분한다. 인벤토리만 새것이고 퍼즐만 옛것인 혼합 복구는 피한다.

## 13. 환경·생활 기능과 RP 연결

출처: 원문 L489–L508.

이벤트는 실제 상태 전이가 확정된 사실을 전달한다. 제안 payload 는 eventId, chatKey, mapId, sourceId, kind, stateRevision, gameTime, 실제 동행 IDs, 필요한 결과 참조다. 개인정보나 대화 전문을 불필요하게 복제하지 않는다. 이벤트 이름은 기존 bus 허용 목록에 등록하기 전에는 동작한다고 가정하지 않는다.

3 번 퍼즐 외 아홉 기능의 접점과 첫 범위
1 지역 퀘스트: clueInspected, puzzleSolved, artifactRestored 를 읽어 진도 계산. 선행 발견도 인정한다. ‘닫힌 빛의 길’ 한 이야기를 먼저 끝내며 토트 신전은 후속 연구다.
2 발굴·감정·복원: excavationClaimed 와 artifactRecovered 를 고유 유물 ID 에 연결. 출토·소유·감정·복원은 별도 단계다. 첫 유물의 확정 파편과 08 서비스부터 연결한다.
4 날씨: environmentChanged는 안전 순간에만 지형을 바꾼다. 10의 맑음/바람 이후와 20의 영구 발견을 분리한다. 현실 시간 대기·확률 날씨로 필수 진도를 잠그지 않는다.
5 NPC 일정: 08 의 서비스 가능 상태와 만난 사실을 기록한다. 상인·복원 담당·여행자 소수 일정부터, 필수 서비스는 의뢰함 등 대체 경로를 둔다.
6 집 전시: artifactRestored 뒤 소유품을 기존 집의 제한 슬롯에 설치한다. 소유와 배치는 다르며 치워도 유물이 사라지지 않는다. 새 집 맵은 범위가 아니다.
7 탐험 수첩: 장소·단서·유물·퍼즐 완료 원천 사실을 고유 키로 집계한다. 공개 탐사 분모에 미발견 비밀을 넣지 않고 기존 달성 보상은 기준 버전 변경 후에도 보존한다.
8 교역: 일반 자원만 거래에 연결한다. 핵심 유물·봉인석 판매 불가. 실제 접근 가능한 두 거점의 소수 상품부터 검토하며 미제작 지역 배송을 강제하지 않는다.
9 동행 특기: 실제 동행 중 함께 조사한 사실과 추가 관찰만 기록한다. 혼자 얻는 필수 단서 대안을 유지하고 감정·호감도·관계 상승을 자동 기록하지 않는다.
10 야영·준비: campRegistered, restCompleted, safeReturnRegistered 를 연결한다. 게임 시간과 보급품 사용은 명시적 행동에서만 진행한다. 앱이 닫혀 있었다고 자원을 소진하지 않는다.

동일 완료를 여러 소비자가 받아도 일지·퀘스트·보상을 중복 생성하지 않게 각 소비자는 eventId 또는 의미 키로 멱등 처리한다. 최근 사건 목록이 잘려도 영구 완료·보상 원장은 없어지지 않아야 한다. 전체 이벤트 소싱 엔진으로 갈아엎기보다는 기존 facts 와 영구 상태를 연결하는 좁은 어댑터부터 만든다.

RP 는 별도의 사용자 선택 경로다. ‘빛 우물에서 장치를 작동해 벽감을 열고 제례 유물을 회수했다’처럼 실제 완료 사실만 미리 보여 준다. 사용자는 항목을 선택·수정·제외하고 대화에 넣을 수 있어야 한다. 미리보기 편집은 RP 문장만 바꾸고 게임의 완료·소유 상태를 바꾸지 않는다. 실제 함께 있지 않은 캐릭터, 캐릭터의 기쁨·감동·대사, 플레이어가 하지 않은 행동을 덧붙이지 않는다. 승인 전 자동 주입·자동 전송하지 않는다.

기존 prepared 사건과 메시지 연동을 활용할 수 있지만 현재 그것이 새 검토·수정·제외 UI 를 제공한다는 뜻은 아니다. 채팅 전환·swipe·regenerate·메시지 삭제 후 같은 사건이 다른 대화에 붙지 않는지 함께 검사한다.

## 14. 입력·접근성·로딩·성능

출처: 원문 L510–L522.

장치를 선택한 뒤 가능한 행동만 큰 버튼으로 제공한다. 터치 드래그와 정밀 각도 조절은 필수가 아니다. 겹친 장치는 선택 목록, 작은 단서는 조사 확대본을 사용한다. 멀리 있는 장치를 눌렀을 때 접근 이동인지 설명만 보는지 기존 조작과 일관되게 정하고, 벽을 뚫고 조작하지 않게 접근점을 검사한다.

캔버스 오브젝트는 키보드로 순회 가능한 상호작용 목록과 텍스트 상태를 함께 제공한다. 선택 포커스, 회전·집기·삽입·회수·닫기 동작, 잠금 이유를 표시한다. 색에만 의존하지 않는 수신부 문양, 비활성 핀, 빈/삽입 소켓 표현을 사용한다. 효과 감소 모드에서도 광선 방향과 성공 여부를 읽을 수 있어야 한다. 조작 후 상태 변화는 과도한 반복 없이 텍스트로 알린다.

한 번의 탭을 canvas 와 DOM 이 중복 처리하지 않도록 전파·pointer capture·취소를 다룬다. 선택한 오브젝트가 맵 변경·획득으로 사라지면 메뉴를 닫고 stale 핸들러를 무효화한다. 앱 백그라운드, pointercancel, 패널 닫기에서 이동키나 드래그가 눌린 채 남지 않게 한다.

현재 맵 필수 에셋을 우선 로드하고 인접 맵은 여유가 있을 때만 예열한다. 34 개 공간의 40 장 원본·밤 그림·장치 전 상태를 시작 시 모두 decode 하지 않는다. 모바일에서 실측한 메모리 예산으로 캐시를 제한하고 오래 쓰지 않은 decoded 이미지·오프스크린 버퍼를 해제한다. 에셋 ID 와 버전으로 공용 장치를 재사용한다.

정적 배경은 재사용하고 움직이는 작은 효과만 갱신한다. 광선 dirty 상태를 따로 관리해 카메라 이동·선택 깜빡임마다 전체 광학 계산을 하지 않는다. 재입장 때 RAF, 타이머, ResizeObserver, 이벤트 구독, 이미지 콜백, 오디오 핸들이 중복 쌓이지 않도록 owner 단위 dispose 를 둔다. 가시성 변경 때 불필요한 애니메이션을 줄이고 복귀 시 정확한 상태를 한 번 재계산한다.

성능 수치는 실제 지원 기기와 현재 베이스라인을 측정한 뒤 목표로 정한다. 이 문서는 임의 FPS·해상도·완성 날짜를 확정하지 않는다. 측정 항목은 진입 지연, decode 메모리, 장치 조작 반응, 프레임 비용, 반복 진입 후 잔존 리소스다.

## 15. 개발 오버레이와 자동·수동 검증

출처: 원문 L524–L551.

개발 화면에 보행 도형, 캐릭터 발 도형, 포털 트리거·스폰·방향, 장치 피벗·광선 법선·선분·종료 사유, 선택 영역, 가림 순서, 현재 chatKey 의 비식별 디버그 표시, puzzle revision 과 rewardClaims 를 표시한다. 정답·비밀 이름·단서 그래프는 개발 모드에서만 보인다.

데이터 검사
- 34 공간·40 원본 등록 수와 상태 그림 분류가 맞고 번호 재정렬로 ID 가 바뀌지 않는다.
- 기본 연결의 모든 역방향 entry 가 존재하며 잠금 전후 발 도형이 통과한다.
- 출입 스폰이 목적지 트리거·물·벽·닫힌 문 안에 있지 않다.
- 모든 필수 단서가 완료 전 접근 가능하고 정보 그래프에 자기 잠금이 없다.
- 승인 상태와 실제 에셋 파일·manifest 버전이 맞는다. 누락 최종 에셋을 완료 처리하지 않는다.

순수 로직 검사
- 광학 해석 상세 단위시험은 원문 §14 L536–538 및 §7에 위임한다. 맵 통합에서는 벽 차단·맵 경계 종료·결정성·저장 복구 후 같은 결과를 확인한다.
- 돌 소유 합계와 소켓 점유가 모든 조작·거부·초기화 후 보존된다.
- 해결 → 돌 회수 → 초기화 → 재입장 뒤 solvedEver 와 보상 수령은 유지된다.
- 동일 claim 두 번, 저장 재시도, 빠른 연속 터치에서 유물은 한 번만 생긴다.

통합과 수동 검사
- 15 입문부터 16 결합, 08 감정·복원, 기존 집 전시, 일지까지 한 번 이어서 완료한다.
- 왕복·사선 접근·두 포털 경계·문턱 위 회수·막힌 스폰을 시험한다.
- A 조작 중 B 전환, A 로딩 중 B 전환, 늦은 hint/save/talk 콜백이 B를 바꾸지 않는다.
- 저장 실패·손상·구버전·미래 버전·복원에서 기존 아이템과 완료 기록을 지킨다.
- 작은 화면·회전·확대·키보드·색 구분 어려움·효과 감소 모드를 확인한다.
- 기존 옴보스·두아트 이동, 낚시·상점·거처 출입, RP 메시지 수정 동작을 회귀 검사한다.

현재 검사 도구가 통과해도 위 전체가 검증되는 것은 아니다. 이번 문서 작성 중 실제 앱·테스트는 실행하지 않았다. 기존 문서에 기록된 알려진 실패와 이번 변경이 만든 실패를 구분해 결과표에 ‘통과/실패/미실행/환경 차단’을 적는다.

## 16. 전투 구역의 공간 배치 계약

출처: 원문 L553–L653.

배치 후보는 확정 스폰 좌표가 아니다. 문서의 전투 구역 7역할을 실제 분할된 9공간으로 추적한다. 몹을 배경에 그려 넣지 않고 spawn 데이터로 배치한다. 맵마다 입구 안전구역, 일반몹 구역, 회피·준비구역, 보스 구역, 조사/보상 구역을 표시한 오버레이를 만든다.

### T1 제례 앞뜰: T1W + T1E
- 후보: 가죽 방패병, 봉인 항아리. 서쪽/동쪽은 별도 맵과 스폰 집합이다.
- 큰 마당에서 일반몹 2~3 개체 한 무리부터 검토한다. 이는 초기 검토 수량 제안이며 채택 개체 수가 아니다.
- 입구에 즉시 돌진 판정을 놓지 않는다. T1W의 15 연결 문과 남쪽 두 귀환 경로, T1E-B 계단·E-C 열린 길·오른쪽 T2 연결 문을 몹·상자로 막지 않는다.
- 두 맵 모두 연결·귀환 검수. 모든 후보를 한꺼번에 소환하는 기본값 금지.

### T2 무너진 봉헌품 회랑
- 후보: 봉인 항아리, 태양거울, 빈 가면 사제 장막형.
- 중앙 벽 양쪽 순환로를 유지하고 광선 회피 폭·엄폐를 확인한다. 태양거울은 실제 발사점에서 별도 광선이 나가며 벽 뒤까지 맞히지 않는다.
- 퍼즐 반사판과 적 태양거울은 선택 표시·이름·공격 예고로 구분한다. 몹을 돌리는 것이15/16 퍼즐 조작으로 처리되면 실패다.
- 왼쪽 15 귀환·오른쪽 T1E 순환·남쪽 11 출구·북쪽 T3 진행을 각각 검수한다. 기록/유물은 선택 탐험 보상, 필수 퍼즐 단서는 전투 획득품으로 옮기지 않는다.

### T3 신전 수호문 전당
- 후보: 천칭 파수꾼, 안쪽 신전 수문장.
- 일반몹 구간과 보스 사이에 시야가 트이는 준비 공간. 첫 검토는 보스 단독으로 시작해 예고·회피·공격 범위부터 확인한다.
- 남쪽 T2 귀환과 북쪽 큰 문을 통한 16 접근을 검수한다. 보스 패배/퇴각 후 T2 복귀를 보장한다. 큰 문 통과 조건·필수 처치 여부는 미정이며 연결 확정만으로 새 전투 잠금을 강제하지 않는다.

### P1 고대 장례 미궁
- **최신 배치 결정: 천칭 파수꾼. 다른 종 추가는 보류.** 원문의 가죽·봉인 방패병·걸음 비석 후보는 과거 안이며 현재 배치에 되살리지 않는다.
- 큰 개체를 좁은 통로에 끼워 통행·회피를 막지 않는다. 개체 수·좌표는 실제 승인 데이터와 화면으로 검증한다.
- 순환로, 막다른 조사실, 상단 12A·하단 12B·동쪽 P3A 출입구를 구분한다. 몹 배치로 의도한 갈림길을 일방통행으로 바꾸지 않는다.
- 최신 세로 채택본만 사용. 반려 가로 미궁이나 다른 시안을 런타임 충돌 원본으로 쓰지 않는다.

### P2 왕면 열병 전실
- 후보: 봉인 방패병, 안쪽 왕면 수문장.
- 13 봉인 해제 후 입장하고 14 로 이어진다. 최신 결정: 왕면 첫 처치로 14 접근을 영구 해제한다.
- 13 안전 퇴각을 보장한다. 최초 처치·영구 개방과 현재 보스 존재 상태를 분리하며 재출현해도 14를 다시 잠그지 않는다.
- 주먹 내려찍기의 준비 자세와 실제 공격 구역, 후딜 반격 기회를 확인한다.

### P3 부왕 장례전: P3A 장례선 봉안실 + P3B 석관 안치전
- 권역 후보: 빈 가면 사제 수의형, 왕좌 수문장.
- 최신 결정: P3A에 빈 가면 사제 수의형, P3B에 왕좌 수문장. 개체 수·정확한 위치는 기존 승인 배치와 실제 여유 바닥에서 검증한다.
- 왕좌 수문장을 양쪽 방에 복제하지 않는다. 보스 한 주역이라는 원칙을 지킨다.
- P1 귀환, P4 동쪽 분기, P3B 남쪽 운반로를 모두 보존한다. 이 선택 분기의 보상으로 13·14 필수 열쇠를 만들지 않는다.

### P4 무너진 왕릉 하부실
- 후보: 걸음 비석, 안쪽 파릉 수문장.
- 긴 팔의 뻗기/붙잡기 예고와 바닥 회피 공간. 준비구역 이후 보스 단독부터 검토한다.
- P3B 로 돌아오는 선택 종착지다. 부장고로 가는 임의 지름길이나 다섯 번째 보스를 추가하지 않는다.

### 추가 운반로와 보상방
- 운반로의 소규모 일반몹 무리는 문서상 가능하지만 종·개체 수는 미정이다. 새 필수 열쇠·보스·잠금은 추가하지 않는다.
- 황금 부장고, 지하샘 보물방, 전망맵, 휴식·생활방에 출처 없는 전투를 추가하지 않는다.
- 나머지 맵에 후보가 없다는 것은 ‘영구 전투 금지 확정’과 다르다. 이번 적용에서는 임의 spawn 을 만들지 않는다.

### 각 배치 레코드에 필요한 항목(제안)
spawnId, speciesId, mapId, 발 위치, facing, encounterId, home/roam 영역, aggro 조건, leash 영역, 공격 프로필, 처치 보상, 재출현 정책, 검수 상태. 모든 좌표·범위는 채택 맵과 실제 캐릭터 크기로 측정한다. 원본 PNG 크기를 타일 개수로 착각하지 않는다.

### 16.1 맵 쪽에서 보장할 전투 인터페이스

출처: 원문 §16 L642–653의 공간·충돌·저장 접점만 추출. 상세 공격 상태 기계, 모션 타이밍, 피해·가드 수치는 이 문서의 구현 범위가 아니다.

- 추격·이탈·귀환 경로는 사용자 수동 충돌을 따른다. 직선 지름길로 벽을 뚫지 않으며 입구·회복 장소를 적이 영구 점유하지 않는다.
- 원문 L641의 보스 약 2.5배는 작화 목표다. 실제 몸체 표시를 비교해 검증하며 PNG 캔버스 배율 2.5를 일괄 적용하지 않는다.
- 발/부유 중심, 물리 크기, 이동 콜라이더, 공격 도형, 발사 소켓, 가림은 서로 구별한다. 거대한 PNG 전체나 섬광 알파 경계를 보행 충돌로 쓰지 않는다.
- 돌진의 이동 경로 전체를 검사해 얇은 벽 관통을 방지한다. 근접 공격·광선은 벽 너머 판정과 가림 정책을 검증한다.
- 태양거울 별도 광선 출처: `docs/art/desert-sun-mirror-motion-revisions-2026-10-16/beam.png`. 길이·방향·벽 차단을 실제 발사점에서 처리하고 PNG를 벽 너머까지 단순 늘리지 않는다. 작은 모래·먼지·충격 효과는 기존 FX/코드 재사용을 우선한다.
- **최신 재출현 계약:** 일반몹과 모든 보스는 게임 내 하루 경과 + 재입장에서 재출현한다. 최초 처치/최초 보상/영구 통로 개방과 현재 encounter 상태를 분리한다. 현재 HP·공격 프레임을 영구 저장하는 문제와 처치 사실·최초 보상 기록은 구별한다. 로드 직후 공격 중간 프레임으로 기습하지 않는다. 채팅 소유권·중복 보상 방지는 저장 계약을 따른다.
- 사막 12종·120장과 기존 고대장치 2종·20장은 별개다. 기존 고대장치나 두아트 작업을 이 배치 문서로 임의 변경하지 않는다(원문 L655–656).

## 17. 채택 배경·상자·오브젝트 상태

출처: 원문 L658–L689.

배경에 있는 모든 물건을 새 투명 PNG 로 다시 그릴 필요는 없다.
- 고정 장식: 채택 배경 그대로.
- 조사만 하는 그림: 원본 위 상호작용 영역과 필요한 강조/확대만.
- 열림·닫힘: 정렬된 국소 상태 패치 또는 승인 상태 배경을 근거로 파생.
- 운반석·움직이는 거울: 원래 자리의 빈 바탕과 독립 sprite 가 필요.
- 가림: 필요한 전경 부분만 분리하거나 기존 전경 재그리기 경로를 검증.

## 18. 사용자 수동 충돌 원본 적용

출처: 원문 L691–L706.

**현재 지시:** 기존 승인 수동 충돌이 있다. 16의 확인된 경로는 `사막맵/충돌/16_빛우물.png`이며, 기존 Drive `사막맵 충돌` 폴더를 대조할 수 있다. 아래는 원본을 새로 요구하는 목록이 아니라 기존 데이터를 가져와 일치시키는 계약이다. 실제 경로가 문서에 없으면 최신 저장소·작업 브랜치·생성기·제공 자료를 먼저 찾는다. 현재 파일을 확인하지 않은 상태에서 ‘충돌 없음’으로 표시하지 않는다.

최우선 원칙: 사용자가 한 장씩 정밀하게 그린 경계가 승인 원본이다. 자동 색상 선택·부정확한 AI 추론·큰 사각형·과도한 다각형 단순화로 교체하지 않는다. 원본이 없는 맵은 ‘미확정’으로 표시하고 임시 경계를 승인품처럼 배포하지 않는다.

권장 전달 계약
- 배경 원본과 동일 캔버스 크기·원점인 별도 충돌 PNG 또는 기존 승인 경계 데이터.
- 색/알파가 의미하는 walkable/blocked/미정 값을 사용자 파일 방식에 맞춰 명시한다. 색을 보고 임의 추측하지 않는다.
- 원본 파일·해시·크기·배경 버전·변환행렬·적용 후 차이 검사를 보존한다.
- 축소가 필요하면 보행 마스크의 경계 변화량과 좁은 통로 손실을 먼저 보여 준다. 자동 팽창/침식으로 모양을 바꾸지 않는다.
- 발 도형 크기에 따른 통과 여부와 사용자가 그린 원본 경계를 분리한다. 보행자 반경을 고려한다고 원본 마스크를 영구 변형하지 않는다.
- 동적 문·닫힌 벽감·운반석은 승인 정적 마스크 위 별도 blockers 다. 문 상태가 바뀌면 모든 이동 소비자와 캐시가 동시에 갱신되어야 한다.

맵별 검수
채택 배경 위에 사용자 원본 경계, 적용된 경계, 플레이어 발 도형, 출입 트리거·착지를 각각 다른 색으로 표시한다. 화면 확대·축소에서도 선과 지면이 함께 움직이는지 본다. 벽 가까이 직선·대각선·돌진, 좁은 계단, 기둥 뒤, 큰 몹 주변, 문 열림 전후, 동행, 포인터 이동을 확인한다.
이미지의 높은 기둥 전체를 보행 금지로 막는 것과 발이 닿는 받침을 막는 것은 다르다. 가림·보행·광선 차단·전투 피격 도형은 각각 목적에 맞게 둔다. 사용자의 정밀한 경계가 코드에서 엇나가면 원본을 다시 그리게 하기 전에 origin/scale/crop/DPR/카메라 역변환을 검사한다.
모든 맵을 사용자에게 다시 수작업시키는 것을 기본 대안으로 두지 않는다. 이미 있는 승인 데이터 가져오기·좌표 일치·차이 오버레이·작은 수정 이력 보존부터 지원한다.

### 20.1 최신 결정 반영 후 남은 확인 항목

- 20 ↔ 보물방의 기존 실제 문턱, 전망 오벨리스크의 승인 워프 목적지/착지를 확인한다. 보물방 위 계단은 전망맵 전용이다. 문이 없다고 추측하거나 임시 포털을 추가하지 않는다.
- 맵별 정확한 스폰 위치·개체 수, 최초/반복 보상 구성, 실패·퇴각 복구는 현 구현·최신 승인에서 확인한다. 재출현 조건 자체는 최신 결정(게임 내 하루 경과 + 재입장)을 따른다. 가드·피해 수치는 전투 담당 범위다.
- 기존 사용자 수동 충돌의 정확한 파일 경로, 색/알파 의미, 배경 버전, 변환을 확인한다. 16을 누락하지 않는다. 검색하지 않고 파일 부재를 단정하거나 재전송을 요구하지 않는다.
- 15 높이 차 광학 접점, 필요한 빈 바탕·상태 그림, 황금 부장고의 독립 상자 수/보상은 현 자료를 대조한다.
- 사용자 언급 27장 작업 묶음과 34공간의 대응을 확인한다. 별도 신규 전투 7맵이라는 이유만으로 34에 다시 7을 더하지 않는다.
- P2와 P3 역할 분배는 더 이상 미정 질문이 아니다. 상단 최신 결정 표대로 적용하고 정확한 현 좌표만 검증한다.

src/core/data.js
실제 MAPS 명시 목록, loadData(), loadJson(), ensureSceneArt(mapId). 신규 맵은 실제 등록 방식에 추가해야 한다. data/maps/*.json의 referenceScenes와 data/scene-art.json을 확인한다. 신규 manifest 자체가 기존 로더 지원 기능은 아니다.

src/ui/window.js
실제 onSpot(id, fn), onTile(fn), onOpen(fn), gameUi(), travel(mapId, pos=null). pos 는 {x, y, dir} 또는 named entry 문자열을 받는다. onTile 은 발이 새 타일에 들어갈 때와 맵 진입에 호출된다. 따라서 포털 영역 안 연속 프레임을 전제로 한 새 판정은 별도 설계가 필요하다.
travel은 moving guard, closeCards, s.pos 대입, await saveState, await enterMap, refresh 흐름과 finally 해제를 사용한다. enterMap은 ensureSceneArt 후 실패 시 옴보스로 fallback한다. 새 장면 전환은 이 기존 fallback·소유 채팅 동작을 검토해야 한다. 현재 읽기에서 채팅/요청 세대 stale guard는 확인되지 않았다.
talk의 지연 use(target)는 mode/card를 재확인하지만 맵/채팅 변경 후 오래된 target 차단은 신규 보강 과제로 다룬다.

src/world/things.js 및 index.js
실제 addThings(fn(mapId, state) → 오브젝트 배열). 항목은 id, x, y, label, sprite, act(ui, map), 선택적 pose 등을 사용한다. 이는 그리기·상호작용 경로이며 동적 충돌 등록 API 가 아니다. 고정 spot 은 onSpot, 신규 pack 등록은 index.js side-effect import 관례를 따른다. 새 퍼즐 순수 해석기는 이 어댑터 안에 모두 섞지 않는다.

src/world/map.js
GameMap 캐시 키는 mapId, 열린 overlay 목록, era에 기초한다. 신규 퍼즐의 문 닫힘/돌 상태까지 자동 반영되지 않는다. revision 기반 무효화 또는 동적 blockers 합성을 설계한다. authoredCollision의 pixelWalk와 polygon 경로를 모두 고려한다. solidRect는 pixelWalk 분기에서 changedCells를 보지 않으므로 overlay만 추가하면 모든 동적 문 충돌이 해결된다고 가정하지 않는다.

src/world/reference-scene.js 및 data/scene-art.json
기존 scene 필드에는 file/nightFile, lazy, origin, scale, crop, clip, occluders, tintActors, tintWorld 등이 있다. 실제 가림은 polygon·foot 및 act/look/dir 조건으로 같은 승인 배경을 다시 그리는 경로다. 별도 투명 전경 PNG, 상태별 거울, 동적 광선은 새 지원 범위를 검증해야 한다. 현재 맵의 해상도·scale 값을 신규 맵 공통 규격으로 복사하지 않는다.

src/core/state.js
실제 STATE_VERSION=12, freshState(), getState(), saveState(); ctx().chatMetadata[MODULE]와 ctx().saveMetadata(). 마이그레이션 STEPS와 fill, 객체당 1회 처리 WeakSet을 사용한다. 큰 상태 필드 추가 시 freshState만 고치지 말고 fill 객체/배열 목록도 검토한다. 미래 버전은 다운그레이드하지 않으나 fill은 실행되므로 미래 필드 보존을 시험해야 한다. s.duat는 기존 카드 원정 진행이며 공간 퍼즐 전용 저장이 아니다.

src/packs/adventure/engine.js
resolve/begin/current/hint와 follow,touch,find,bring,choice,overlay 흐름이 있으나 s.adv.cur 기반 소모험이다. 실제 반사광·봉인석 공간 엔진이 이미 있다는 근거가 아니다. 전용 puzzle 엔진은 읽기 조사에서 발견되지 않았다.

src/core/inject.js, src/core/news.js, index.js

생성물과 테스트

src/core/check.js의 checkData는 rows/legend/spot bounds/anchor tilewalk 등을 검사하지만 전체 출입 목적지·발 도형 경로·퍼즐 풀이 가능성까지 보장하지 않는다.
기존 문서의 검사 후보: tools/art/verify-full-map.cjs, verify-cozy-ui.cjs, verify-ui-themes.cjs, tools/st-test/duat-maps.cjs, residence-exits.cjs, records68.js. 실행에는 동작 중인 SillyTavern과 문서상 NODE_PATH 환경 등이 필요하다. package.json 기반 프로젝트로 가정하지 않는다.
verify-browser.cjs 의 알려진 두 실패는 기존 handoff 기록이며 이번에 재현한 결과가 아니다. 기존 폰 크기·낮밤·출구 검사 시나리오를 재사용하되 신규 장면 전부의 합격으로 확장 해석하지 않는다.
