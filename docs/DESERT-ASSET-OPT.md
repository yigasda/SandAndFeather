## 2. 바꾼 것

- `tools/art/desert-mob-pack.py`: **원본보다 크게 묶지 않는다**(배율 상한 1). 배율이 1이면 원본 픽셀을 그대로 옮긴다(크기 변환·알파 보정을 거치지 않음). 확대는 화면에 그릴 때만 한다(`visible` = 시트에서 캐릭터 키 하나가 몇 px인지; 게임은 `H / visible`로 같은 크기로 그림).
- 작은 묶음이 원본보다 커지는 종(수문장 4종)은 큰 묶음과 **같은 시트를 함께 쓴다**(파일 하나). 그리기 코드는 쓰는 중인 시트를 놓지 않게 고쳤다(`field.js drawMob`).
- 원본 해상도로 다시 묶은 7종(수문장 4종·천칭·봉인 방패병·장막형), 70프레임 모두 **원본과 픽셀 단위로 같음**(색·알파 그대로, 검사함). 나머지 5종(축소 묶음)은 그대로다.
- 종별 분리, 장당 4096 제한, 원본 PNG(`몹/사막/…`)는 그대로다. 표시 크기·피격 도형·공격 판정은 바꾸지 않았다(도형은 원본 px 기준이라 같은 값).

## 4. 화면 비교 (흐림·발 위치)

폰 412×900 dpr 2의 T1W에서 캐릭터 키 하나 = 약 140 화면 px이다(넓은 PC dpr 2는 280). 신전 수문장은 폰에서 약 590 px 높이로 그려진다. 이전에는 미리 키운 1075 px 그림을 줄여 그렸고, 지금은 353 px 원본을 약 1.7배 키워 그린다.

- **발·몸·주먹 위치:** 7종 × 5모션(대기·준비 1·공격·피격·소멸) × 두 화면 크기를 게임과 같은 방식으로 그려, 불투명 영역의 왼·오른·위·아래 끝(기준점에서 잰 화면 px)을 비교했다. 차이는 최대 2 화면 px(반올림 수준)다. → [result.txt](consult/desert/mobs/art-compare/result.txt)
- **흐림:** 원래 크기에서는 구분하기 어렵다. 4배로 키워 보면 지금 쪽 경계가 아주 약간 부드럽다(이전: 미리 Lanczos로 키움, 지금: 브라우저 고품질 확대). 화면 확인:
  - 실제 게임 화면(폰, 같은 모션으로 고정): [신전 수문장](consult/desert/mobs/art-compare/game-temple_warden-pair.jpg) · [4배 확대](consult/desert/mobs/art-compare/game-temple_warden-zoom.jpg) · [파릉 수문장](consult/desert/mobs/art-compare/game-broken_tomb_warden-pair.jpg) · [4배 확대](consult/desert/mobs/art-compare/game-broken_tomb_warden-zoom.jpg)

## 5. 메모리·로딩

`node tools/st-test/mob-art-memory.cjs <out> [--old <이전 sprites.json>]` — 폰 412×900 dpr 2, CPU 4배 느리게, 로컬 서버(내려받는 시간 없음). 장면마다 몹을 세우고 **모든 모션(대기 순환·준비 0/1·공격·후딜·가드·피격·소멸)을 재생한 뒤** 잰다. 예정 배치(DESERT-REGISTRY)에 가까운 구성이고, P2는 아직 게임에 없어서 T1W에 세웠다. 같은 종 여러 마리는 시트 하나를 같이 쓴다(가죽 방패병 2 + 항아리 1 = 시트 2장, 7.3 MB).

| 장면 | ① 사막 몹 그림(픽셀 계산) 전 → 후 | 그림이 보이기까지 전 → 후 |
|---|---|---|
| T1 예정: 가죽 방패병 2 + 봉인 항아리 1 | 7.3 → 7.3 MB | 420 → 445 ms |
| P2 예정: 봉인 방패병 2 + 왕면 수문장 1 | **60.9 → 12.3 MB** | 795 → 345 ms |
| 가장 큰 보스: 파릉 수문장 1 + 걸음 비석 2 | **95.7 → 16.6 MB** | 689 → 433 ms |
| 맵 왕복 3번 뒤 T1W | 5.3 → 5.3 MB(쌓이지 않음) | |
| 두아트 04 | 0 → 0 (사막 그림 남지 않음) | |

세 가지를 구분한다.

1. **픽셀 계산**(지금 쥐고 있는 그림의 가로×세로×4). 위 표 외에 같은 장면 전체는 캐릭터 그림 194.0 MB, 맵 배경 6.0 MB, 화면 캔버스 5.8 MB가 더해진다. → **캐릭터 그림이 몹보다 훨씬 크다**(이번 범위 밖, 따로 볼 항목).
2. **측정한 값**(이 컨테이너의 헤드리스 크롬):
   - JS 힙 35~54 MB. 그림 대부분은 JS 힙에 잡히지 않는다.
   - 렌더러 프로세스 RSS: 전 800~958 MB → 후 795~907 MB. SillyTavern 페이지 전체 값이고, 한 번 늘어난 RSS는 잘 줄지 않아 장면 순서에 따라 계속 오른다. 그림 몫만 따로 떼어낼 수 없다.
   - 헤드리스라 GPU 프로세스가 따로 잡히지 않았다.
3. **측정하지 못한 것:** 실제 폰의 GPU 텍스처 메모리, 브라우저 내부 이미지 캐시(디코딩을 버렸다가 다시 하는지), 폰 브라우저의 탭 메모리 한도, 실제 내려받는 시간. 궁 이펙트는 아직 게임에 없어 포함하지 않았다(적용 뒤 다시 잰다).

## 6. 큰 묶음과 작은 묶음

- **쓰는 조건:** 화면에서 캐릭터 키가 `small.visible + 1` px 이하면 작은 묶음, 넘으면 큰 묶음을 쓴다(`drawMob`). 큰 묶음이 준비되면 작은 것은 놓는다.
- **언제 어느 쪽:** 폰 dpr 2의 T1W는 140 px로 큰 묶음을, dpr 1 폰·멀리 보는 대형맵은 작은 묶음을 쓴다.
- **배포에 둘 다 있는 이유:** 기기마다 화면 밀도가 달라서, 어느 쪽을 쓸지는 실행할 때 정해진다.
- **용량:** 지금 일반 8종의 작은 묶음은 합해서 파일 3.7 MB(디코딩 10.1 MB)다. 수문장 4종은 큰 묶음과 같은 파일이라 추가 용량이 없다.
- 작은 묶음을 빼면 dpr 1 화면에서도 큰 묶음을 쓰게 된다(메모리 증가). 확인 없이 지우지 않았다.

## 7. 궁 이펙트 (아직 게임에 안 넣음)

`docs/art/skill-effects/final/` 채택본(세트 7·호루스 7·소망 6)을 조사했다. **완전히 투명한(알파 0) 여백만** 잘라도 크다. 희미한 빛·연기(알파 1~31)가 그림의 20~90%를 차지하고, 모두 남긴다.

| | 캔버스 | 잘라낸 뒤 가장 긴 변 | 전 프레임 디코딩: 원본 → 여백만 자름 | 파일 |
|---|---|---|---|---|
| 세트 모래폭풍 | 2400×2000 | 1881 | 128 → 59 MB | 3.7 MB |
| 호루스 충격파 | 3200×3200 | 2560 | 273 → 150 MB | 5.7 MB |
| 소망 연꽃 방패 | 2800×2600 | 2048 | 167 → 94 MB | 3.0 MB |

화면에 그려질 크기는 2번 시제품에서 궁 범위가 정해져야 나온다. 그 크기에서 게임용 해상도 후보(원본·1/2·1/3)를 나란히 보여 드리고 확인받는다. 원본은 그대로 둔다. 임의 축소는 확정하지 않는다.

## 8. 폰에서 확인할 것

지금 T1W에는 문이 없어서, 폰에서는 시험 이동 없이 사막 몹을 볼 수 없다. 폰 확인용 이동 방법이 정해지면 체크리스트대로 본다.

- [ ] 수문장이 나오는 장면에 들어가서 처음 보일 때까지 끊김이 있는지(첫 진입, 내려받는 시간 포함)
- [ ] 수문장의 경계·주먹·상형문자가 흐리게 보이지 않는지(폰을 눈 거리에서)
- [ ] 수문장 뒤에 서면 반투명이 되고, 가장자리에만 걸치면 그대로인지
- [ ] 맵을 여러 번 오간 뒤 버벅임·화면 깜빡임·탭 재시작이 없는지
- [ ] 다른 앱을 갔다 와도 그림이 비지 않는지
