## 0. 만들기 전에 — 생각하고, 찾고, 확인받는다 (사용자 강력 요청)

사용자가 같은 종류의 실수를 반복해서 지적했다. "왜 내가 이런 걸 하나하나 말해줘야 해", "내가 말한 거 말고도 다 참고해"라고 했다. 할당량도 계속 버려졌다. **지시문만 글자 그대로 처리하지 말고, 이 작업에 무엇이 필요하고 무엇이 빠져 있는지 스스로 추론한다. 그리고 제작 전에 계획을 확인받는다.**

**실제 사례 — 호루스 정면 걷기 132·133번.**
- 실수: 기존 인게임 걷기 PNG가 `art/chibi-refresh/approved/walk/`에 프레임별로 이미 있었다. 그런데 그걸 열어 보지 않고 걷기 동작을 임의로 만들었다.
- 결과: 발 위치만 맞추고 발 방향과 원근, 다리가 겹치는 방식, 치마가 들리는 모양, 발 크기를 놓쳤다. 다리를 비비는 듯한 이상한 동작이 됐고, 발이 좌우로 커서 정면이 아니라 크리처 걸음처럼 보였다.
- 그런데도 아틀라스와 참고 파일이 일치한다는 검증만으로 모션까지 맞췄다고 말했다.
- 사용자가 저장소 링크를 직접 줘서야 고쳤다.

**제작 전 반드시 할 일.**
1. **있는 것부터 찾는다.** 저장소에서 이 작업과 관련된 기존 파일을 먼저 검색해서 연다. 승인 원본, 프레임별 PNG, `manifest.json`, 게임 아틀라스, 이전 검토본과 반려 사유가 대상이다. 예: 걷기는 `approved/walk/<캐릭터>-<방향>-<0|1|2>.png` 36장, 정지는 `approved/idle/` 12장.
2. **추론한다.** 다음을 스스로 짧게 정리한다.
   - 사용자가 진짜 원하는 결과
   - 그걸 위해 반드시 지켜야 할 것: 기존 동작의 프레임별 특징, 채택된 외형, 크기와 발 기준점
   - 지금 부족한 것: 참고 파일, 정보, 프레임
   - 어떻게 검증할지
   - 사용자가 말하지 않았어도 당연히 따라와야 하는 조건. 예: 걷기면 발 방향·원근·다리 겹침·치마와 팔의 움직임·발 크기·머리 흔들림까지 기존과 같아야 한다.
3. **확인받는다.** 이미지를 생성하거나 편집하기 전에 사용자에게 짧은 계획을 보내고 OK를 받은 뒤 만든다.
   - 계획에 넣을 것: 베이스 파일, 바꿀 것, 지킬 것, 방법, 결과물 개수, 검증 방법.
   - 사용자가 범위를 명확히 정해 준 국소 수정은 바로 해도 된다. 새 동작, 새 장면, 전체 편집, 여러 장 생성은 반드시 먼저 확인받는다.
4. **비교해서 검증한다.** 모션은 프레임마다 기존 PNG와 나란히 놓고 위 항목을 하나씩 대조한다. 일부만 확인해 놓고 "맞췄다", "완료"라고 말하지 않는다. 확인하지 않은 항목은 확인하지 않았다고 쓴다.
5. **사용자에게 당연한 것을 설명하게 만들지 않는다.** 사용자가 파일이나 예시를 언급하면 그 파일 전체를 열어 본다. 말한 부분만 고치고 나머지 특징을 버리지 않는다.

**모든 일에 생각부터 한다.** 지시에 적힌 단어만 처리하지 않는다. 그 결과가 기존 그림 안에서 자연스러울지 먼저 판단한다.

**실제 사례 — 우물 마당 입구 116·117번.** "입구를 추가해"라는 요청에 대해 오른쪽에 식당 안을 통째로 들여다보는 큰 문을 만들었다.
- 투시가 기존 마당과 맞지 않았다.
- 기둥과 문 크기가 기존 건축보다 컸다.
- 안쪽 식당이 마당과 다른 각도와 크기로 그려져, 다른 그림을 붙여 넣은 것처럼 보였다.

사용자가 원한 건 이 마당에 원래 있었던 것 같은 입구였다. 입구를 추가하라는 말에는 아래 조건이 당연히 포함된다. 따로 말하지 않아도 지킨다.
- **투시:** 기존 장면과 같은 시점·각도·소실 방향. 바닥 타일선, 벽 두께, 천장선이 그대로 이어진다.
- **규모:** 기존 기둥, 문, 가구와 같은 크기 체계. 캐릭터가 지나갈 만한 크기이되 장면에서 튀지 않는다.
- **화풍:** 같은 도트 밀도, 같은 팔레트, 같은 빛 방향과 그림자.
- **안쪽 묘사:** 문 너머에 방 안이나 바깥 풍경을 그려도 된다. 오히려 그게 그림을 풍성하게 만든다. 다만 같은 장면 안에서 문을 통해 들여다본 모습이어야 한다. 바깥 마당과 같은 시점과 원근으로 안쪽으로 이어져야 하고, 가구와 소품 크기도 기존 체계를 따른다. 116번처럼 다른 각도로 그린 그림을 문틀 안에 붙여 넣은 듯 보이면 안 된다. 입구가 "저쪽으로 갈 수 있다"는 길로 읽히는지도 함께 확인한다.
- **낮밤:** 같은 위치·형태. 밤에는 빛만 바꾼다.

**전달 전 마지막 질문.** 결과를 보내기 전에 원본과 나란히 놓고 스스로 묻는다.
- 처음부터 이 그림의 일부였던 것처럼 보이는가?
- 사용자가 "이거 왜 이래"라고 설명해야 할 부분이 있는가?

하나라도 걸리면 보내지 말고 고치거나, 계획 단계로 돌아가 사용자에게 묻는다.

## 1. 가장 중요한 원칙

> 사용자는 **채택된 시안을 베이스로만 고치는 것**을 원한다. 마음에 든 그림을 계속 다듬는 작업이지, 같은 설명으로 비슷한 그림을 새로 만드는 작업이 아니다.

- 수정 대상은 설명이나 기억이 아니라 **실제 채택 파일**이다. 파일을 열어 보고, 그 파일을 편집 입력으로 삼는다.
- 요청한 부분만 바꾼다. "이것만"은 범위를 제한하는 말이다. 안광 하나를 지우면서 동공을 바꾸거나, 출구를 고치면서 가구를 옮기면 실패다.
- 요청 밖 요소가 바뀐 결과는 다음 베이스로 누적하지 않는다. 채택본에서 필요한 부분만 가져온다.
- 합쳐 보여 달라는 요청은 기존 파일을 배치하는 작업이다. 합본을 새로 그리지 않는다.
- 전체 재작성은 사용자가 그 범위를 명시했을 때만 한다.
- 원본 위에 단순 도형, 단색, 어색한 그림자를 얹어 마무리하지 않는다.

**한 번에 하나씩.** 사용자가 작업량 때문에 품질이 떨어진다고 했다. 여러 대상을 동시에 만들지 않는다. 한 대상의 비교 시안을 확인받고 피드백을 반영한 다음 넘어간다.

**할당량 아끼기.** 하루에 프로 할당량 93%를 쓴 적이 있다.
- 고칠 부분만 잘라서 작업한다. 확인도 작은 크롭이나 3배 확대로 한다. 큰 PNG 여러 장을 반복해서 다시 읽지 않는다.
- 원본 복사, 마스크, 리사이즈, 합성으로 되는 수정에는 이미지 생성을 부르지 않는다.
- 전후 비교판은 사용자에게 보여 줄 때 한 장만 만든다.

## 2. 상태를 구분하는 법

**최신 파일 ≠ 채택된 파일 ≠ 게임에서 쓰는 파일.** main에 커밋했거나 Drive에 올렸다는 사실은 채택의 증거가 아니다.

| 상태 | 의미 | 다룰 때 |
|---|---|---|
| 채택된 원본 | 사용자가 선택·승인한 실제 그림 | 국소 수정의 기준. 보존한다 |
| 수정 검토본 | 요청을 반영해 새로 전달한 결과 | 자동 승인 아님. 승인된 요소만 계승 |
| 반려·교체본 | 사용자가 싫다고 했거나 후속본으로 대체됨 | 기본 입력에서 제외 |
| 게임 적용본 | 코드가 실제로 읽는 에셋 | 경로로 확인. 시안 전달만으로 적용 완료라 하지 않음 |

부분만 채택될 수 있다. 예: "얼굴형·헤어만 채택, 명암은 반려". 부분별 출처를 따로 적는다. 새 검토본에 답이 없다고 승인됐다고 추정하지 않는다. 이미 정해진 취향과 승인은 다시 묻지 않는다.

## 4. 다음 할 일 — [ASTRA-PLAN.md](ASTRA-PLAN.md) 요약

위 열린 작업은 사용자와 이어서 마무리한다. 그다음은 계획서 순서대로 한다. 위에서부터 하나씩.

1. **안채 마무리: 긴 회랑 5장 끝통로 넓히기 + 세로 887px(11칸)로 맞추기.** 안쪽 복도부터 먼저 한다. 기존 그림은 픽셀 그대로 두고 바깥만 늘린다. 끝 기둥 바깥 통로 폭은 1.5칸(약 120px) 이상.
2. **셋소호 동작 바리에이션.** 기본(달리기·상호작용·줍기) → 생활 동작 → 전투·상태 순서. 발 기준점과 배율은 승인 48장 규칙을 따른다. **치비 리프레시가 채택되면** 새 그림체로 4방향 정지·걷기를 먼저 만들고, 동작도 그 기준으로 만든다.
3. **두아트 확장.** 맵 4개, 효과, 그리고 몬스터: 일반은 인게임 4종, 수문장 2, 문지기 아펩의 비늘(채택), 보스. 강한 적은 아펩의 비늘에 씌인 존재로 그린다. 아펩 본체는 따로 대형 이벤트로 둔다. ① 경계 동굴 1차 시안이 있다([DUAT-EXPANSION-ART-V1.md](DUAT-EXPANSION-ART-V1.md)).
4. **새 지역.** 사막·베헤데트 → 강가와 여행 지도 → 테베 → 토트 신전.

**게임 적용은 오푸스가 한다.** 사용자가 아스트라와 정리한 파일을 한꺼번에 넘기면, 오푸스가 맵 크기·충돌·출구·가림·밤 전환을 맞춘다. 아스트라는 런타임 파일(`tools/maps/`, `data/`, `src/`)을 고치지 않는다.

## 6. 셋소호의 채택 기준

근거는 [승인 원본 폴더](art/chibi-refresh/approved/)와 [48장 목록](APPROVED-IDLE-WALK-FILES.md)이다. 아래 설명은 파일을 찾고 잘못된 변경을 막는 메모일 뿐이다. 설명만 보고 캐릭터를 다시 생성하지 않는다.

- **몸 비율:** 세 명의 몸 베이스는 호루스다. 세트 옆모습의 배가 불룩해지거나 하체가 길어지지 않게 한다. 머리 모양 때문에 생긴 외곽 차이를 몸 비율 문제로 오해하지 않는다.
- **세트:** 긴 자주색 머리, 눈매. 곧은 옆선, 짧은 차콜 치마.
- **소망:** 눈매와 얼굴, 시스루뱅, 가슴 길이의 퐁실한 곱슬 끝, 흰 드레스와 흰 끈리본. 치비 검토에서는 다크브라운 머리이고, 곱슬은 살리되 옆 폭은 부풀리지 않는다.
- **호루스:** 짧고 삐죽한 푸른 남색 머리. 검게 보이거나 길어지거나 두상이 찌부되지 않게 한다. 피부는 밝은 뉴트럴 쿨톤이고 웜하게 되돌리지 않는다. 작은 동공과 아래 안광. 왼쪽 눈 문양의 방향별 비대칭은 무조건 미러하지 않는다. 가슴천 없음.
- **걷기:** 0→1→2→1, 180ms. 호루스 정면만 360×400 셀 기준 `(+1,0), (0,-1), (-1,0), (0,-1)` 오프셋을 쓴다. 회전은 추가하지 않는다. 오프셋을 PNG와 렌더러 양쪽에 중복 적용하지 않는다.

## 7. 맵 보정의 기준

- 채택 장면의 구도·색·가구·재질·화풍을 유지한다. 바꾸는 건 요청한 부분뿐이다.
- 입구는 건물과 같은 구조와 원근을 가진다. 기둥 높이, 천장선, 벽 두께, 바닥선이 이어져야 한다.
- 입구가 가구 뒤에 떠 보이면 문틀만 키우지 않는다. 통행 바닥부터 만든다.
- 낮밤 쌍은 같은 위치·형태로 고친다. 밤에는 약한 등불만 더한다.
- 그림 크기는 기본적으로 고정이다. 예외는 사용자가 허용한 것뿐이다.
  - 연못 회랑: 오른쪽 +484px (확정).
  - 긴 회랑: 좌우 확장 + 세로 887px (계획 1단계).
  - 우물 마당 432px 확장 수치는 반려된 규격이다.
- 크기를 바꾸면 원본이 놓인 위치(오프셋)와 새 그림 기준 좌표를 함께 준다. 편집 영역, 문턱, 제안 트리거, 제안 도착점을 구분해서 적는다.
- 좌표는 제안만 한다. 실제로 걸어 본 것처럼 말하지 않는다. 통과 검증은 오푸스가 한다.

## 9. 저장소와 전달

- 저장소: https://github.com/yigasda/SandAndFeather, 브랜치 `main`. 새 환경에서는 실제 체크아웃 경로부터 확인한다.
- 오푸스도 같은 main에 작업한다. 커밋 전에 원격을 받아 오고, 강제 푸시나 다른 작업 덮어쓰기는 하지 않는다.

- 이미지 결과는 Google Drive 링크로 준다. 사용자가 폰에서 인라인 이미지나 로컬 링크를 못 연 적이 있다.

- 새 지시를 받으면 이 문서의 해당 칸(3절 표, 5절 표)을 고친다. 경과는 위에 계속 쌓지 말고, 길어지면 `archive/`로 옮긴다.
